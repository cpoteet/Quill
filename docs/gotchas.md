# Quill — cross-cutting gotchas

Indexed by title in the root `CLAUDE.md`.

Most file-specific gotchas moved to per-directory `CLAUDE.md` files on 2026-07-11 so they load only when Claude is working in that directory: `Sources/QuillKit/Resources/`, `Sources/QuillKit/Views/Editor/`, `Sources/QuillKit/API/`, `Sources/QuillKit/Views/Media/`, `Sources/QuillKit/Views/Sidebar/`, `Sources/QuillKit/App/`, `Sources/QuillKit/AI/`, `Sources/QuillKit/Views/AI/`, `Sources/QuillKit/Views/Settings/`, `Sources/QuillKit/Views/`. What's left here is cross-cutting or doesn't map to one directory.

- **The toolbar-wide fade on inspector toggle is an implicit `sublayers` CATransition on the toolbar's glass hosting view, and `InspectorTitlebarFix` nulls that action** — while the inspector's split-view animation context is open, SwiftUI swaps the sublayers of the `_NSCoreHostingView<NSGlassEffectContainerView.RootView>` that hosts every glass-backed toolbar item (`NSThemeFrame > NSTitlebarContainerView > NSTitlebarView > NSToolbarView > NSGlassContainerView > hosting view`), and CoreAnimation's default action for a `sublayers` change inside an implicit-animation context is a 0.25s fade `CATransition`. Everything inside the glass fades, including Preview and Update; the status glyph (`.sharedBackgroundVisibility(.hidden)`, so no glass) and the inspector's own button do not, which is why it read as "only the thin icon buttons flash". `InspectorTitlebarFix` already runs on every `NSSplitView.didResizeSubviewsNotification`, so it sets `layer.actions = ["sublayers": NSNull()]` on that hosting view there; `contents` alone was not enough, `sublayers` alone was, and nothing else animates on the toolbar afterwards. Measured 2026-09-19 with a probe that walked the window's view tree every 16ms after each resize and logged any layer with live animation keys, then a per-button crop over 360 frames at 60fps: baseline 2 fades (min 0% of median dark pixels), fixed 0. The media inspector has no fade without the fix and is not wired to it. Same symptom is reported for macOS 27.0 at <https://developer.apple.com/forums/thread/845735> (FB24782376), whose author only got as far as naming the layer. Ruled out on the way: `withAnimation` around the toggle (identical without it), item churn, key-window loss, titlebar geometry, and sidebar-vs-detail ownership.

- **Measure the region the user is describing, not the whole strip** — a fade confined to three small glyph buttons is invisible to a dark-pixel average taken across the entire toolbar; it falls under the threshold and reports zero. That produced several false "fixed" conclusions during the 2026-09-19 toolbar-flash investigation. Crop to the control in question and re-measure. The companion error is not checking that the action under test actually happened: two runs looked clean only because an unverified click missed and no post ever opened — read the post title out of the captured frames to confirm.

- **`AppState` orders taxonomies once, on assignment — the settings panel never sorts** — `categories` and `tags` are computed properties over private `@Published` storage, and their setters call `Array.sortedByName()` (`WPTaxonomy.swift`, locale-aware `localizedCaseInsensitiveCompare`). Every assignment site is covered, `append` included, so inline tag/category creation keeps the order. `PostSettingsPanel` therefore does no sorting at all and relies on its inputs already being ordered; its `filter`s preserve order. This is not cosmetic: sorting 243 tags inside a computed property re-ran on every body evaluation and, together with building all 243 rows eagerly, stalled the main thread enough to fade the toolbar on every inspector open. Both halves are needed — the panel's two nested lists use `LazyVStack`, and removing only one of the two did not fix it. A single sort benchmarks at 1.07ms, so the cost was repetition, not one slow call.

- **A carried attribute is a script sink — everything the raw-attribute carrier snapshots gets replayed onto the live contenteditable** — the carrier stores a loaded element's own attributes and writes them back on save, and in between they sit on real DOM inside the privileged WKWebView, where an `on*` handler from post content executes with the bridge in scope. `isCarryableAttr(name, value)` in `editor.html` filters at snapshot time: any `on*` attribute is dropped, and `javascript:`/`vbscript:`/`data:text/html`/`data:image/svg` values are dropped from the URL-bearing attributes. It must be applied at *every* snapshot point — `elementAttrPairs` (block nodes), `_attrMap` (the `rawInline` mark) and `LinkWithRawAttrs.rawAttrs` — because each one is an independent path from post content to the DOM. A new carrier of any kind needs the same filter. Guarded by `test-editor-preservation.js`'s `'an attribute that could run script is not carried'`.
- **The unsupported-block sentinel is a per-save random nonce, and must stay one** — `toWordPressHTML` swaps each preserved block for a text placeholder before serializing, then substitutes the bytes back. The placeholder used to be the fixed string `QUILLUNSUPPORTED<n>QUILLEND`, which an author can simply type into a post; the first-occurrence `String.replace` then moved the preserved block's bytes to wherever that text sat. It is silent — the block count is unchanged, so the tripwire stays quiet. The nonce is now generated per save and substituted with a single global-regex pass. Guarded by `'preserved block bytes cannot be relocated by post text'`.
- **The block-risk banner only blocks saving once the body has been edited** — `PostEditorView.alarmBlocksSaving` is `blockRiskAlarm?.blocksSaving == true && htmlContent != cleanContent`. An untouched post saves `_rawHTML` back byte-for-byte and cannot lose anything, so making the user click through a content-deletion warning for a lossless save is noise. Every write path checks it, not just the two that originally did: `save(status:)`, `performAutosave`, `flushToDB` (the post-switch flush) and `saveLocalOnly` (⌘S on a local draft). A new write path has to join them.
- **`_reportBlocksAtRisk` posts its list on every load and code-view edit, empty list included** — the empty report is how the editor says a post is clean, which is what lets a banner clear itself after the user repairs the post in code view. `PostEditorView.nextAlarm(from:names:)` is the other half: an empty report clears the banner, the same names again preserve an existing `.acknowledged`/`.saved` stage rather than re-raising it, and a different list raises it afresh. Any test that asserts "nothing was reported" has to compare the *names*, not the message count.
- **`build.sh` copies each `Resources/` file by name — a new resource needs its own `cp` line or it 404s at runtime** — the assemble step lists `editor.html`, `AppIcon.icns`, `tiptap-bundle.js`, `editor-transforms.js`, `marked-bundle.js`, `block-parser-bundle.js`, `block-serializer.js`, `block-descriptors.js`, `block-settings.js` individually rather than copying the directory. Swift builds fine and tests pass (jsdom loads from the source tree), so a missing line only shows up as a silently undefined global in the running app.
- **A top-level `const` in a Resources JS file is NOT reachable as `window.x` from `editor.html`; only `function` declarations are** — classic scripts share one global lexical scope, so a top-level `const` is reachable by *bare identifier* from another classic script but never as a property of `window`/`globalThis`. This matters because `editor-transforms.js` resolves `block-descriptors.js` as `globalThis` in the browser and as a CommonJS `require` under Node, so `blockDescriptorRegistry.SOME_CONST` silently reads `undefined` in the app while working perfectly in every Node test. Cost a real bug on 2026-09-12: `blockNeedsWrapping` read `BLOCK_DESCRIPTORS` (a `const`) to decide which blocks Quill models, got an empty set in the browser, and wrapped every paragraph in the post into a frozen passthrough card — with the whole JS unit suite green. Anything a Resources file must expose across this boundary has to be a `function` declaration (`modelsBlockName` in `block-descriptors.js` is the pattern), or explicitly assigned to `window`. The only test that catches this class of bug is one running in the real-`editor.html`-in-jsdom harness, not the pure-Node one.
- **New JS dependencies get their own bundle script, not a `bundle-tiptap.sh` edit** — that script's package.json pins `"^2"`, so re-running it npm-installs Tiptap fresh and can drift the editor onto a newer 2.x. `Scripts/bundle-marked.sh` (→ `marked-bundle.js`, `window.MarkedBundle`) and `Scripts/bundle-block-parser.sh` (→ `block-parser-bundle.js`, `window.BlockParser`) are the pattern: same esbuild IIFE recipe, separate file, so adding a parser never forces an editor upgrade.
- **Synchronous image work must not run on the main actor** — `ImageConversion.prepareForUpload` is a blocking ImageIO decode + JPEG re-encode. Its two SwiftUI callers (`PostEditorView.handleDroppedImages`, `MediaSidebarSection.uploadFromDisk`) are MainActor-isolated via `View` conformance, so calling it inline froze the UI for the whole conversion — visibly, on a large photo. Both now wrap it in `await Task.detached(priority: .userInitiated) { … }.value`. `uploadPickedImage` was already off the main thread. Any new upload path must do the same.
- **Anything that writes `uploadStatus` must go through `dropTask`** — the `UploadStatusPill` (`DesignSystem.swift`, `View.uploadStatus(_:)`) and the toast share **one** bottom-center slot. Overlapping Finder drops raced on the shared `uploadStatus` state: a second batch dropped while the first was still uploading cleared the pill early and let a toast and the pill render on top of each other. `PostEditorView` holds `@State private var dropTask: Task<Void, Never>?` and `onImageFilesDropped` chains each batch onto the previous one (`await previous?.value`), so batches never interleave. Any future code path that shows the pill must join the same queue rather than writing `uploadStatus` directly. Pure SwiftUI view plumbing with no extractable helper — no unit test; manual check is in `docs/testing-plan.md` §7.4.
- **Ad-hoc signing** — `build.sh` signs with `-`; "Always Allow" on keychain prompts won't persist across rebuilds (irrelevant now that credentials use file storage, but WKWebView may still prompt once per binary for its own internal keychain use)
- **Editor link colour is one CSS variable per theme** — `--link` on `:root` (light) and `body.dark` (dark) in `editor.html`. Prose links, footnote markers and footnote backrefs all read `var(--link)`; none carries its own colour. Driven by `body.dark` alone, not `prefers-color-scheme` — the media-query fallback the toolbar chrome uses would paint dark-theme links when the app is explicitly light on a dark system. Markers and backrefs used the amber accent (`#b45309`/`#d97706`) until 2026-09-13, and light prose links had no rule at all, falling through to WebKit's default `#0000EE`.
- **Color tokens & surface components** — the warm-surface era is over. `wpSidebarBg`, `wpPanelBg`, `wpTitleBarBg`, `WarmSidebarBackground`, `WarmPanelBackground`, `WarmPanelHeaderBackground`, `SoftPanelBoundary`, `SoftHorizontalDivider` and `PanelInteriorFade` are all deleted (native-ui, 2026-09-18). Use system materials and plain `Divider()`. `DesignSystem.swift` now holds only `Color.wpContentSurface`, `statusColor(_:)` (whose `"draft"` case uses a file-private `draftAmber`), `ToastView`, `UploadStatusPill` and their modifiers. The app has no accent colour of its own — it follows the user's System Settings accent, so `Color.accentColor` is the right token for a selection, focus ring or action, and a semantic colour (a status dot, a warning) must never be the accent.
- **`Color.wpContentSurface` and `editor.html`'s page colour are one value in two files and must move together** — the editor surface spans a SwiftUI view and a WKWebView, so the same colour is declared twice: `Color.wpContentSurface` in `DesignSystem.swift` (white in Aqua, `#242424` in Dark Aqua) and the `body` / `--toolbar-bg` / `#editor-wrap` declarations in `editor.html`. Change one without the other and the title field steps against the webview. **Do not reach for `NSColor.textBackgroundColor` as the dark value** — it reports `#1E1E1E`, which is the flat token, not what a `NavigationSplitView` detail column actually renders (a material compositing to about `#242124`). Trusting it made the editor visibly darker than the rest of the window. Verify by sampling the rendered pixels, not the token; Apple Mail is the reference, at `#252123` content against a `#2C2529` sidebar. `ContentView` also carries `.toolbarBackground(.hidden, for: .windowToolbar)`, which is what lets each column's background reach the top edge of the window instead of sitting under a toolbar material band.
- **A view placed in an `.inspector` must not set its own width** — `.inspectorColumnWidth(min:ideal:max:)` on the inspector content is what makes the divider draggable. `PostSettingsPanel` and `EvaluationPanel` each ended with `.frame(width: 260)`, which pinned both panels at the minimum and made the divider look dead (fixed 2026-09-19). Below roughly a 1030pt window the inspector is squeezed under its declared minimum instead; that is SwiftUI's own trade-off and the fix for it is a wider window, not a `.frame`.
- **Re-expanding the inspector needs `InspectorTitlebarFix`, or the panel stops below the toolbar** — the first time the inspector opens, AppKit gives the content pane and the inspector one `NSTitlebarBackgroundView` each, split at the divider, so the panel's background reaches the window's top edge. On every later expansion the content pane's stays at full window width and is re-added last, so it paints an opaque band over the inspector's first 52pt and the panel appears to start below the toolbar. Only the frame is wrong, and AppKit rewrites it after `NSSplitView.didResizeSubviewsNotification`, so the correction has to ride the *view's own* `frameDidChange` notification: `InspectorTitlebarFix` (a zero-size `NSViewRepresentable` in the inspector's `.background`) trims the content band back to the inspector's left edge each time it grows past it. Reordering the two views instead does not hold — SwiftUI re-raises the content band on the next layout pass. Diagnosed 2026-09-19 by dumping the window's view tree on open and close.

- **`SectionLabel` is the one uppercase caption above an inspector or sheet section** — it lives in `DesignSystem.swift` and takes the title in ordinary case (`SectionLabel("Alt text")`); it applies `.textCase(.uppercase)` and `tracking(1.0)` itself. Four files previously spelled this idiom five different ways, some pre-uppercasing the string and some dropping the tracking. Do not hand-roll another `Text(...).font(.footnote.weight(.semibold))` caption.
- **Sheet actions go in a bottom bar, never in a top header row** — macOS puts the dismissing actions at the bottom trailing edge and a non-dismissing action (Upload…) at the bottom leading edge; the sheet's title, when it has one, is a top-leading `.font(.headline)`. `MediaPickerView`, `GallerySheet` and `SamplePostPickerSheet` used an iOS-style Cancel-left / centred-title / action-right bar until 2026-09-19. A sheet also never presents a second sheet in place of an alert — use `.alert`.
- **`.textFieldStyle(.plain)` is the house style for every text field** — with `.padding(5–7)` and `.overlay(RoundedRectangle(cornerRadius: 5).stroke(.separator, lineWidth: 1))`. Every field in the app follows it (`PostSettingsPanel`'s slug field is the reference). `.roundedBorder` draws a system blue focus ring that appears nowhere else, so it reads as a bug the moment a field is clicked.
- **Verify saved draft HTML straight from SQLite rather than through the UI** — a local draft is written only on an explicit Save Draft, so `sqlite3 ~/Library/Application\ Support/Quill/drafts.db "select content from local_drafts order by updated_at desc limit 1;"` is the fastest ground truth for what Quill actually saves. The `autosaves` table holds remote posts only and stays stale for local drafts. Code view is not a substitute — it shows `formatHTML`-pretty-printed content, not the bytes.
- **jsdom and Chrome both lie about ProseMirror's empty-node caret** — an empty inline node view renders a `<br class="ProseMirror-trailingBreak">`, and in WebKit that break is the *only* caret target the node has. Hiding it (`display: none`) lays out correctly in Chrome and passes every jsdom test, while making the node completely uneditable in the real app. `:has()` on that break is no better: WebKit does not re-evaluate it when the break is removed. Track empty state with a class the node view sets in its constructor and `update()` instead — `FootnoteItemNodeView`'s `fn-item-empty` is the pattern. Any CSS that keys off ProseMirror's own rendering artifacts has to be checked in Quill, not a browser.
- **Background computer-use clicks do not reach the WKWebView's DOM handlers** — `app_click` reports ok but toolbar dropdowns never open and the editor does not respond. Testing editor UI needs `request_full_control`; the app_* tools are fine for reading the window.
- **Scripted clicks do not focus an `NSViewRepresentable` — only real `CGEvent` clicks do** — both `app_click` and AppleScript `tell application "System Events" to click at {x, y}` report success, and the accessibility layer even reports a caret placed in the field, but the view's `mouseDown` never fires and first responder never moves. Reading the field back then shows it empty, which looks exactly like a broken control. This cost a wrong root-cause call on the sidebar search field (2026-09-19): three fixes were built and an AppKit approach was declared unsound, all from an artifact of the harness. Verify any focus, click or typing behaviour in an AppKit-backed view with `request_full_control` and the display-scope tools, never with the scripted ones. Sibling of the WKWebView entry above; the cause is the same and the class of view is wider than that entry implies.
- **Unicode curly quotes in Swift strings** — Swift treats `"` (U+201C) and `"` (U+201D) as string delimiters, identical to ASCII `"`. Do not use curly quotes inside string literals with interpolation — use escaped ASCII quotes `\"...\(value)...\"` instead.
