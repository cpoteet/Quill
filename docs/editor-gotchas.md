# Editor gotchas (`editor.html` / `editor-transforms.js`)

Full text of the gotchas indexed by title in `Sources/QuillKit/Resources/CLAUDE.md`. Read the entry before changing the code it describes.

- **Every attribute the carrier snapshots reaches the live contenteditable, so the snapshot is a security boundary** — `isCarryableAttr(name, value)` drops `on*` handlers and `javascript:`/`vbscript:`/`data:text/html`/`data:image/svg` URL values, and it has to be called at all three snapshot points (`elementAttrPairs`, `_attrMap` for the `rawInline` mark, `LinkWithRawAttrs.rawAttrs`) because each is an independent path from `post_content` into the DOM. A new carrier needs the same call. Full entry in the root `CLAUDE.md`.
- **The placeholder `toWordPressHTML` leaves where a preserved block was must be unguessable** — it is a per-save random nonce substituted back with one global-regex pass. A fixed token can be typed into a post, and the old first-occurrence `String.replace` then relocated the preserved bytes to that text, silently. Full entry in the root `CLAUDE.md`.
- **The trailing-paragraph strip must name the shapes it follows, or it eats a real block** — the editor keeps an empty paragraph after a block the caret cannot get past, and `toWordPressHTML` removes it again on save. Removing "the last child if it is an empty `<p>`" also removes an empty `core/paragraph` an author wrote at the end of a post — and invisibly to the tripwire, which counts block names and sees one paragraph either way. The condition is scoped to exactly the shapes `TRAILING_PARAGRAPH_AFTER` follows: a preceding `table`, `figure`, `hr`, unsupported wrapper or passthrough card. The footnotes list is not body content: both `TrailingParagraph` and the strip look at the last block before a trailing `ol.wp-block-footnotes`, or a post with footnotes gets no paragraph after a final table (↓ lands in a footnote) and keeps an empty one on save.
- **Tab must be handled by the editor, or WebKit moves focus to a caption, summary or button inside the post** — an unhandled Tab runs WebKit's sequential focus navigation from the caret. Image captions were editing hosts of their own until cpoteet/Quill#24 removed the `-webkit-user-modify` rules (see the caption entry below), and `<summary>` and `<button>` are focusable even inside a contenteditable, so the caret jumped to the next caption, wrapping to the top of the post. `TabKey` runs at priority 1, after the list and table keymaps: it inserts `\t` in a code block or Preformatted and otherwise swallows Tab and Shift-Tab. Patching one focusable target at a time does not work; the next one takes over.
- **Code-type text opts out of smart quotes with a `spellcheck="false"` decoration, never a rendered attribute** — WebKit applies the system's smart quotes and dashes to contenteditable text but skips anything inside `spellcheck="false"`, which is how the code view `<textarea>` and Custom HTML sheet already avoid them. `_chromeDecorations` adds it to `codeBlock` and `preformatted` as a node decoration and to inline-code text as an inline decoration, so it never reaches `getHTML` or the save. ProseMirror draws the inline decoration's span inside the `<code>`, not around it.
- **`/^\s+/` in JavaScript matches U+00A0, so a whitespace strip deletes deliberate `&nbsp;` indentation** — the leading-whitespace strip on top-level paragraphs exists for the newline a bare-text parse turns into a space; it now uses `/^[\n\r\t ]+/`. Any strip that means "layout whitespace" has to spell the characters out rather than lean on `\s`.
- **A passthrough card is only byte-for-byte if its markup is stashed out of the way, not just shielded from the comment-strip regex** — `gutenbergPassthrough` content is swapped for a nonce placeholder alongside the unsupported wrappers, before the style-compaction and void-element passes run. Shielding it from the comment strip alone was not enough: ProseMirror's style re-serialization turned `style="color: red"` into `style="color:red"`, and the void-element pass turned `<img src="x">` into `<img src="x"/>`. Both are invisible to the block tripwire and both diff the post.
- **A `<li>` holding two or more paragraphs is left alone on purpose, even though core's rich-text `<li>` will flag it** — `toWordPressHTML` unwraps a single-child `<p>` inside an `<li>` (and a leading one before a nested list), but a genuinely multi-paragraph item keeps its `<p>` tags, because unwrapping would run the two paragraphs together and lose the break. Normal editing cannot produce the shape — Enter inside a list item makes a new list item, not a second paragraph — so it only arrives from a paste or from classic content that already had it, and a core-authored `<li>one<br>two</li>` round-trips byte-identically. Do not "fix" this by unwrapping; the test pinning it is `test-editor.js` `'multi-child <li> is left untouched'`.
- **ProseMirror re-serializes any `style` it renders, so a style Quill did not author must never reach it** — `renderSpec` does `a.style.cssText = value`, which parses the declaration into the CSSOM and writes it back normalized: `color:#cf2e2e` became `color:rgb(207, 46, 46)` in both WebKit and jsdom, and WebKit additionally moved the attribute to the end of the tag. Gutenberg compares the stored `style` against what `save()` regenerates from the comment attributes, so every coloured paragraph, heading, list and button was invalidated on the first edit. `replayRawAttrs` now emits a snapshot's `style` as `data-quill-style`; `toWordPressHTML` rebuilds the element's attribute list to rename it back, which keeps both the value and its position verbatim. A style the node itself renders still goes through the CSSOM and is still normalized by the compaction pass — that is correct, since Quill authored it. Anything else carrying a verbatim attribute value needs the same treatment. Inline marks are the one place a carried style must also be seen (a text colour, an underline), so `_drawnStyleAttrs` writes it twice: `data-quill-style` at the source position for the save, and `style` for display. `toWordPressHTML` drops the drawn `style` of any element carrying `data-quill-style`, and `elementAttrPairs` reads the carried copy and ignores the drawn one, so a copy and paste inside Quill keeps core's bytes too (issue 16). The underline's drawn style is also why core's spaced `text-decoration: underline;` survives the compaction pass.
- **Tiptap 3's OrderedList, TableCell, TableHeader, Blockquote and ListItem bring behaviour v2 lacked, and Quill's subclasses turn it off** — Tiptap 3's stock `OrderedList` derives `type` from `list-style-type` and stops rendering `type="1"`, so a styled list saved `type="I"`, which WordPress rejects. `OrderedListWithClass` restores v2's `type` attribute and `renderHTML`. The same extension adds an unkeyed `handlePaste` plugin that turns plain-text `1. a` / `2. b` into a list with `replaceSelectionWith`, straight into code blocks, footnotes, headings and the middle of a paragraph; `OrderedListWithClass.addProseMirrorPlugins` returns `[]`, and Quill's own `handlePaste` takes the behaviour on with the same parser in the cases that are safe (`docs/paste.md`). `TableCell` and `TableHeader` gain an `align` attribute that renders as `style="text-align: …"` on a cell Quill never styled, and read `colwidth` from the table's `<col width>` when a cell has none, which saved `colwidth` on every cell of a classic table (invalid for core/table); `_cellAttrsAsV2` removes `align`, so the raw-attribute carrier keeps it as authored, and reads only the cell's own `colwidth`. `Table` renders through `TableView` (a `div.tableWrapper`) even with `resizable: false`; `View: null` keeps v2's bare `<table>` in the live DOM. `OrderedList`'s `N. ` input rule joins the list above only when it has no `type`; `OrderedListWithClass.addInputRules` adds v2's join for a typed list. `Blockquote` binds Backspace: at the start of a non-first child it lifts that child out and splits the quote, and at the start of a paragraph after a quote it merges the text into the quote's last textblock (the `cite`, in Quill) with the caret after it. `CustomBlockquote` drops that binding, so Backspace joins backward as on v2. `ListItem` registers `listItemBranchingDeleteKeymap` through its own `addExtensions` (so StarterKit's `listKeymap: false` does not reach it), which on Delete at the end of an item outdents the nested branch below; `ListItemWithClass` overrides `addExtensions` to return `[]`. Each has a characterization test in `Scripts/test-editor-preservation.js` (`Tiptap 3 migration: saved markup`) or `Scripts/test-editor-keyboard.js` (`Tiptap 3 migration: keys and clicks`). Before taking any of these behaviours on purpose, change its test first. The schema dump cannot see parse-function bodies, input-rule predicates or node views, which is how the last three got past it.
- **Delimiter attributes must go through `serializeAttributes`, never `JSON.stringify`** — core escapes `--`, `<`, `>`, `&` and `\` so the JSON cannot terminate or corrupt the HTML comment that holds it. `delimiterAttrs` in `editor-transforms.js` is the single wrapper; all five save sites use it. Carried keys also keep the order WordPress gave them (`overlayCarried`), because spreading moved every key the node also computes to the end of the comment and diffed every post.
- **A regex over the final HTML string must treat `<` and `>` inside attribute values as data** — HTML serializers escape `&` and `"` in an attribute value but not `<` or `>`, so an `alt="a <b> tag"` is literal in the output. A naive `<img[^>]*>` ends the match inside the alt text and corrupts it (caught by the gallery suite's deliberately hostile alt strings). The void-element pass uses `(?:"[^"]*"|'[^']*'|[^>"'])*` to step over quoted values.
- **A node with its own node view never sees `renderHTML`, so a block setting can save correctly and still draw nothing** — `renderHTML` is only used for serialization once a node view exists; the canvas shows whatever the view builds. `ResizableImage` builds a `div.image-wrapper` from scratch, so `is-style-rounded` was in the saved markup, in the delimiter, and in the toolbar's active state while being absent from the editor DOM entirely — a block style that looked broken but tested green everywhere. `_applyAttrs` now copies the `is-style-*` token onto the wrapper. Any new setting on a node-view-backed node (image is the only one today) needs the same explicit copy.
- **A decoration that follows the caret cannot double as the display of a stored setting** — `_tabDecorations` marks the visibly active tab from `state.selection.head`, so `tabPanel.isDefaultTab` (stored as `activeTabIndex`) had nothing of its own on screen. It needs a second decoration keyed off the stored value — `is-default-tab` is the pattern, as is the accordion's `is-open` label. Same shape whenever an editor-only affordance and a publishing choice want the same visual slot: give the publishing choice a label, never the affordance.
- **A leaf block in `DELETABLE_BLOCKS` needs `_deletableTarget`, not the ancestor walk** — `_deletableBlockAt` climbs `$pos.depth`, which only ever finds a block the caret sits *inside*. A selected separator is a leaf: the node selection resolves before it, so the walk returns the doc and the ✕ never appeared. `_deletableTarget(state)` checks `selection.node` first and falls back to the walk; both the ✕ and ⌘⇧⌫ route through it. Esc / double-Enter deliberately still use the walk — there is no caret inside a leaf to exit from.
- **Row 2's dividers are marked from JS, not CSS** — each group hides and shows on its own, and `#block-controls` is drawn last by `order: 1` while it sits earlier in the markup, so no sibling selector can tell which shown group is first on screen. A `MutationObserver` on `#toolbar-row2` re-marks `tb-divided` on every shown group but the first in CSS order whenever a group's `style` changes; the `::before` divider keys off that class. The shared metrics (`--tb-gap`, `--tb-pad`, `--tb-h`, `--tb-radius`, `--tb-divider`) are read by row 2, the image toolbar and the inline image popover alike (GitHub issue 20), so change them there, not per toolbar. Tests: `test-editor-block-settings.js` `'the second toolbar row divides the groups it shows'`.
- **Row 2 must not show or hide while a press in the editor is held** — row 2 is in the page flow above `#editor-wrap`, so toggling it moves the post content 34px under the pointer. WebKit then sends a `mousemove` at the same coordinates with the button still down, and the selection follows whatever is now under the pointer. Clicking a heading directly above a table hid the row, the table moved under the pointer, the caret went into a header cell, the row came back, and the selection was stretched back to the heading: hide, show, hide in about 70 ms, ending in a selection from the heading into the table instead of a caret (traced 2026-10-31). A click into a cell turned into a two-cell selection the same way, through prosemirror-tables' drag handling. It only happened when WebKit's move arrived before the release, so it looked random. `updateToolbar()` hands every row-2 change (each group's display, its active states, the `visible` toggle) to `_updateRow2`, which does nothing while `_row2Pressed` is set and runs again on mouseup, so the row keeps its buttons and its space until release and changes once. A drag-and-drop (a grip drag, a dragged selection) never sends a mouseup, so `dragend` ends the press too. Any other lost mouseup (a context menu) is ended 100 ms after a move with no button down; ending it on that move at once was too early, because macOS sends a buttonless move a few milliseconds before the real mouseup, and the row then moved during the release. Only a left press inside `#editor-wrap` counts: toolbar buttons act on mousedown and many tests press them without a mouseup. A jsdom test that presses inside the post without releasing holds row 2 into the next test, so `test-editor-containers.js` releases after every test. The mouseup listener is in the capture phase, so the row still changes before ProseMirror's `handleClick`, which the click-seat code depends on. Tests: `test-editor-block-settings.js` `'the second toolbar row waits for the mouse button to come up'`; the flicker itself is checked by hand (testing plan §7, "Second toolbar row during a click").
- **The inline image popover writes what core's popover writes, and is tested against core itself** — Width and Alternative text applied together on **Apply**, as `format-library`'s `image/index.tsx` does: an existing `style`/`alt` is replaced in place, a missing one is appended, a cleared width writes `style=""`, a cleared alt `alt=""`. `Scripts/core-formats.js` runs core's own Apply through `@wordpress/rich-text` with `@wordpress/format-library` registered, and the `'the inline image popover'` tests compare byte for byte. Two known differences: Width is read from the `width:` declaration and Apply keeps the style's other declarations, where core reads every digit in `style` (`width:150px;height:100px` shows 150100) and drops the rest; core only writes `width`, so its own markup saves identically. And core escapes `<` and `>` in an attribute value and the browser's serializer does not, so alt text holding them saves as `<` where core writes `&lt;` (both valid). The node view keeps `ProseMirror-selectednode` itself, since defining `selectNode` stops ProseMirror adding it, and `update` redraws in place so Apply does not lose the popover.
- **Every `#toolbar-row2` group must carry `class="tb-group"`, and an icon-only group `tb-group-icons` too** — the row's two metric rules key off those classes (`_buildSettingGroups` sets `tb-group` on each generated group). A static span added without the class gets neither rule and its buttons fall back to the 26px icon square, which reads visibly tighter than every text button beside it — how "New tab" shipped wrong. The audit snippet is in `docs/testing-plan.md` §7.24.
- **A widget decoration next to the caret makes WebKit drop every keystroke, and jsdom/Chromium never show it** — the empty-title placeholder on `accordionHeading`/`detailsSummary` started as a `Decoration.widget` holding a `contenteditable="false"` span. In the app the caret landed in the title correctly (verified by logging `editor.state.selection` and `document.getSelection()` out to Swift) and every character typed was silently discarded; the same code typed fine in Chromium and passed in jsdom. Draw placeholder text as generated content (`::before`/`::after`) keyed off a `Decoration.node` class instead — `is-untitled` is the pattern. The details status badge moved from `summary::after` to `.wp-block-details:not(.shows-content)::after` to free the pseudo-element.
- **An empty title inside `.wp-block-accordion-heading__toggle` is zero-width, so a click can never seat a caret in it** — the title span has no text and the absolutely-positioned hint adds no box, so the browser puts the caret in the panel paragraph below and an untitled accordion can never be named. `ContainerChrome`'s `mousedown` handler places it explicitly, but only from a `setTimeout` and without `preventDefault`: preventing the default leaves WebKit with nothing focused and the keystrokes go nowhere, and seating the selection synchronously is undone by WebKit's own click handling straight afterwards.
- **Gutenberg invalidates a block when the stored HTML carries anything its `save()` would not regenerate** — validation re-runs `save()` from the delimiter attributes and compares tokens. Class *order* and empty-valued attributes (`alt=""`) are ignored, but an extra attribute or an extra class is fatal: "Block contains unexpected or invalid content." Three image cases hit this before 2026-09-13 — a WP-resized image whose `style` Quill dropped while leaving `is-resized` on the figure, a Quill-resized image emitting `width`/`height` attributes core stopped writing years ago, and a decorative image keeping `role="none"` without the `isDecorative` attr. `applyImageDimensions` and `imageBlockAttrs` in `editor-transforms.js` now rebuild markup and attrs together; any future image presentation feature must add both halves. A fourth case (2026-09-27) passes the current validator and fails an older one: a style-only `height:auto`. block-library 9.47+ `save()` adds `height:auto` itself when the height attribute is unset, so the style needs no comment attr there; older editors (the Jetpack iOS app's GutenbergKit 0.19.0 ships 9.41.0) rebuild the style from the comment alone. Core's own drag stores `"height":"auto"` in the comment, and so does Quill now. Match what core's *editor* writes, not just what the current `save()` happens to accept.
- **Known unfixed edge case: non-dimension `style` properties on an image are dropped** — Quill models only `width`/`height`, so core's `aspect-ratio`, `object-fit`, `object-position` and border/shadow styles (and their `aspectRatio`/`scale`/`focalPoint`/border comment attrs) are lost on the first edit, which invalidates the block the same way. Unlike the container blocks, `core/image` has no `block-descriptors.js` entry, so it gets none of the `data-quill-block-attrs` carrying that would fix this generically; moving it onto the descriptor path is the real fix.
- **Check Gutenberg's own `save.jsx` before treating a block attribute as editor-only** — `core/details` renders `open={showContent}`, so `open` is genuine `post_content` and stripping it collapses every published details block on the front end; `core/accordion` saves nothing for `autoclose`, so that one really is Quill-internal (`data-autoclose`) and must be stripped on save. Verified 2026-09-12 against trunk, after the Phase 6 plan asserted both were editor-only. Fetch with `gh api search/code` — the block files are `.jsx`, so guessing `raw.githubusercontent.com/.../save.js` 404s.
- **Comment-only block attributes ride through Tiptap on `data-quill-block-attrs`, and `descriptor.ownedAttrs` is what lets a node turn one off** — WordPress keeps attributes like `autoclose` only in the delimiter comment, which ProseMirror's DOM parser cannot see, so the whole attribute object is carried on the element and re-emitted. The carrier alone cannot express deletion: `attrsFrom` returning `{}` is indistinguishable from "this block has no such attribute", so a value the user switched off kept its old setting. `ownedAttrs` names the keys whose absence is meaningful. Only declare a key the node genuinely reads back — an owned key with no round-trip behind it is deleted on the first edit — and never let `columnBlock` own `width`, since Quill has no width UI and the carried value is the only copy.
- **`gutenbergPassthrough` must opt out of modeled figures by class, not by excluding `<figure>` wholesale** — the parse rule was originally the single selector `[class*="wp-block-"]:not(figure)`, on the assumption that Quill's own rules "already own or transparently pass through" every `wp-block-*` figure. Only four do (`QUILL_MODELED_FIGURE_CLASSES` in `editor-transforms.js`: image, gallery, embed, table). Everything else fell through to the generic parser and was destroyed on the next save — verified 2026-08-19 in jsdom against the real `editor.html`: `figure.wp-block-audio` collapsed to a bare `<p>` holding only its caption text (the `<audio>` element gone), `figure.wp-block-video` to an empty `<p>`, `figure.wp-block-pullquote` was silently rewritten as a `blockquote.wp-block-quote`, and WP 7.1's new `figure.wp-block-playlist` lost its wrapper, its `wp:playlist` comments, and its `<figcaption>`. Fixed by adding a second, figure-only parse rule that defers via `isModeledFigure(el)` and otherwise hands off to `parsePassthroughBlock`. Consequence to keep in mind: a *new* figure-rooted block Quill decides to model natively must be added to `QUILL_MODELED_FIGURE_CLASSES`, or passthrough (priority 200) will out-rank its own rule and swallow it. Regression tests: `Scripts/test-editor-passthrough.js`, both the figure-rooted describe block and the modeled-figure guards.
- **A `describe()` whose first test calls `setContent` right after a block that leaves the doc as a single atom node needs a throwaway `setContent('<p></p>', false)` in `before()`** — the same one-shot jsdom/Tiptap quirk already documented in the root `CLAUDE.md` for `extendMarkRange`. Confirmed 2026-08-19 to reproduce on unmodified `editor.html`, so it is a harness artifact, not a code bug; two of the new passthrough/keyboard describe blocks carry the hook for exactly this reason.
- **ProseMirror's two clipboard branches have separate hooks, and `handlePaste` runs *after* the parse, not before** — verified 2026-08-08 by reading `parseFromClipboard` in `tiptap-bundle.js`. The paste handler calls `parseFromClipboard(...)` first to build a slice, then `someProp("handlePaste", fn => fn(view, event, slice))` — so `handlePaste` receives an already-parsed slice and cannot pre-empt `transformPastedHTML`. Inside `parseFromClipboard` the branch is `!!text && (plain || parentIsCode || !html)`: with a `text/html` flavor present it runs `transformPastedHTML`; with **text only** it runs `transformPastedText` and then splits on `/(?:\r\n?|\n)+/` into one `<p>` per line, never touching `transformPastedHTML`. That asymmetry was a live bug — the footnote flatten guard existed only on the HTML hook, so multi-line plain text pasted into a footnote (`footnoteItem` is `inline*`) put line 1 in the entry and dropped the rest *after* the footnotes list as sibling paragraphs. Fixed in the `transformPastedText` hook directly above `transformPastedHTML`; both flatten when `_pasteMustBeInline()` (a footnote, or a title, label, citation or caption, which split their block the same way) and must stay in sync. Outside footnotes, the HTML hook runs `cleanPastedHTML` on every paste and the text hook empties whitespace-only lines (`docs/paste.md`). Code blocks need no guard — `parseFromClipboard` checks `$context.parent.type.spec.code` and inserts raw text before either hook's result is used. Regression tests: `Scripts/test-editor-paste.js`.
- **Anything that inserts generated HTML must strip inter-block whitespace text nodes AND pass `parseOptions: { preserveWhitespace: false }`** — both, not either. ProseMirror wraps the first `\n` between block tags in a blank paragraph even with `preserveWhitespace: false`. This bit the AI-insert path first and then `window.insertMarkdown` (marked emits `\n` between blocks); both now do the same `Array.from(tmp.childNodes).filter(TEXT_NODE && !textContent.trim()).remove()` pass before inserting. `insertMarkdown` additionally trims marked's trailing newline inside `pre > code`, which would otherwise show as an empty last line in every pasted code block.
- **Any new `toWordPressHTML` pass is a whole-tree `div.querySelectorAll(...)` and will reach into `gutenbergPassthrough` subtrees unless explicitly shielded** — `gutenbergPassthrough` elements are stashed out into placeholder divs at the very top of `toWordPressHTML` (before any transform runs) and only spliced back in — completely untouched — right before the final `wp:name` comment-regeneration pass, after every other pass (comment-strip, media-id class, image/heading/list/blockquote/cite/table/footnote/embed/gallery normalization) has already run. This is deliberately a *wide* shielding window, not scoped to just the comment-strip regex: an earlier implementation spliced passthrough elements back in immediately after the comment-strip alone, which left them exposed to the later heading-class/empty-cite-removal/empty-figcaption-removal passes — a nested `<h3>` silently gained `wp-block-heading`, and intentionally-empty `<cite>`/`<figcaption>` elements were deleted, even though the whole point of passthrough is byte-for-byte preservation. If you add a new unconditional `div.querySelectorAll(...)` pass to `toWordPressHTML`, it automatically inherits this protection as long as it's placed between the stash and the splice-back — do not add passes after the splice-back point without auditing whether they should reach into passthrough content.
- **`formatHTML`'s `BLOCK` set changes affect ALL existing content wrapped in that tag, not just the new case motivating the change** — adding `'div'` to `BLOCK` (for `gutenbergPassthrough`'s nested divs to indent in code view) also changed formatting of the pre-existing `EmbedBlock` wrapper (`<div class="wp-block-embed__wrapper">`), whose only child is a text node with a literal `'\n'+url+'\n'` (an intentional raw-newline design, not element children). Without handling this, the div's opening tag got indented but the raw-newline text pushed the URL and closing `</div>` onto unindented lines below it. Fixed by trimming a block tag's inner text when it has no element children at all (`serialize`'s `isTextOnly` check). When adding a tag to `BLOCK`, grep for every existing `renderHTML` that emits that tag and check its actual child-node shape (text vs. element children), not just the new feature's fixture.
- **Every block insert goes through `_blockInsertChain()`, because a block inserted into an accordion heading, tab title, button, quote citation or image caption splits its container** — these three textblocks sit inside a container whose content expression cannot hold a stray block, so ProseMirror's fitting splits the container around the insert: an extra empty accordion, the old panel under a new heading, a Tabs block cut in two, and a Table from an empty button deleting the Buttons block. `_blockInsertChain()` checks `TITLE_CONTAINERS`, adds an empty paragraph after the whole container and moves the caret into it, all in the same chain, so the insert replaces that paragraph and one undo removes both. Tabs, Accordion, Columns, Details, Preformatted and Pullquote go through `_insertContainer(block, targetType, offset)`, which records the insert point inside the same chain, after the move out of a title, and puts the caret in the first `targetType` at or after it. Both simpler rules were wrong and were caught in review: searching forward from the point read *before* the move found the old accordion's own heading, and taking the block that holds the caret afterwards fails mid-paragraph, where ProseMirror leaves the caret in the split-off text. Paste as Markdown follows the same rule even for one line: putting a single paragraph *into* the title would mean inserting an inline HTML string, which Tiptap inserts literally (see the `insertContentAt` entry). A new insert command must start its chain with `_blockInsertChain()`, and a new title-like textblock inside a container needs a `TITLE_CONTAINERS` entry. A quote's `cite` and an image's caption (the `image` node's own inline content) are titles too, resolved in `_blockInsertDepth`: a citation's container is its quote or pullquote (`_citeHostDepth`, since one name cannot cover both), a caption's is the image itself. Without them Paste as Markdown split the quote, and split or replaced the image (cpoteet/Quill#27). Ordinary ⌘V paste into a title is not covered and may split the same way; it needs the real-WebKit paste harness to check. From a table cell the chain likewise moves the caret to a new paragraph after the table, because core reads a block comment inside a cell as a nested block the table cannot hold and deletes it on its next save; the validator does not flag it, only core's re-save shows it. Paste as Markdown passes `intoTableCell: true` and stays in the cell, and Image takes its own inline-image path before the chain. Anywhere else, a caret in a textblock that holds text makes that textblock the container too, because ProseMirror's own insert split a paragraph or heading at a mid-text caret, where the block editor's inserter adds after the selected block; an empty textblock is still replaced, and Paste as Markdown (`intoTableCell`) still lands at the caret, as a paste does. Custom HTML has its own insert, which follows the same rule. Guarded by `block inserts from a container title`, `block inserts from the middle of text` and `block inserts from a table cell` in `test-editor-containers.js`.
- **A container a paste or join must not cross is `isolating`, or ProseMirror replaces or merges it** — `replaceRange`, which every paste goes through, widens the replaced range over each ancestor the caret is at the start of, and stops only at a node whose spec is `defining`, `definingAsContext` or `isolating` (`prosemirror-transform`, the loop under "picks a preferred target depth"). `columnBlock` had none, so an HTML list pasted at the start of the first column replaced the column and landed above the columns block, taking the column's width with it. The joins behind Backspace and Delete also crossed it: two columns merged, a column's first paragraph lifted out, and the paragraph after the block became a third column. - **A click outside every line of a block seats the caret at the block's start or end, so `clickSeatTarget` puts it under the pointer** — a click in a block's padding (a pullquote, Preformatted block, Group, table cell), or in the margin between two blocks, is outside every line box, and WebKit resolves it to the start of the block below, or the end of the block above, whatever the x (measured 2026-10-31 on a pullquote, Preformatted block, Group, paragraphs, list items and columns). Moving the pullquote's padding onto its paragraphs did not change it. `_seatForPress` in `editor.html` keeps WebKit's choice of block and fixes only the x: `posAtCoords` returns either a position inside a textblock (a padding band) or a block *boundary* with `parent: doc` (a gap), so the candidates are the textblock at the position plus the nearest textblock before and after it (`selection.constructor.findFrom(…, true)`), limited to the node `posAtCoords` reports under the pointer (so a click inside an accordion or details title, an image or a separator never reaches a neighbour). Without that, a click to the right of a button on its own row was seated in the paragraph above it. Buttons, image captions and tab, accordion and details titles stay obstacles because they are narrow or shrink-wrapped, or have their own click handling, so a click in their padding still follows WebKit's default (start of the block). Adding a shrink-wrapped block to the list brings the same hijack back for its own row. `click-seat.js` `clickSeatTarget` takes each candidate's first and last line rects and returns the nearest line the click is outside of, or null when the click is on a line, or more than two of that line's heights away (so a click far below the post still goes to its end); a tie goes to the later block. Nothing is prevented on mousedown, so a drag-select or shift-click that *starts* in a band still anchors at the block's start, and a double-click there selects the block's first word.
