# Editor gotchas (`editor.html` / `editor-transforms.js`)

Full text of the gotchas indexed by title in `Sources/QuillKit/Resources/CLAUDE.md`. Read the entry before changing the code it describes.

- **Every attribute the carrier snapshots reaches the live contenteditable, so the snapshot is a security boundary** — `isCarryableAttr(name, value)` drops `on*` handlers and `javascript:`/`vbscript:`/`data:text/html`/`data:image/svg` URL values, and it has to be called at all three snapshot points (`elementAttrPairs`, `_attrMap` for the `rawInline` mark, `LinkWithRawAttrs.rawAttrs`) because each is an independent path from `post_content` into the DOM. A new carrier needs the same call. Full entry in the root `CLAUDE.md`.
- **The placeholder `toWordPressHTML` leaves where a preserved block was must be unguessable** — it is a per-save random nonce substituted back with one global-regex pass. A fixed token can be typed into a post, and the old first-occurrence `String.replace` then relocated the preserved bytes to that text, silently. Full entry in the root `CLAUDE.md`.
- **The trailing-paragraph strip must name the shapes it follows, or it eats a real block** — the editor keeps an empty paragraph after a block the caret cannot get past, and `toWordPressHTML` removes it again on save. Removing "the last child if it is an empty `<p>`" also removes an empty `core/paragraph` an author wrote at the end of a post — and invisibly to the tripwire, which counts block names and sees one paragraph either way. The condition is scoped to exactly the shapes `TRAILING_PARAGRAPH_AFTER` follows: a preceding `table`, `figure`, `hr`, unsupported wrapper or passthrough card.
- **`/^\s+/` in JavaScript matches U+00A0, so a whitespace strip deletes deliberate `&nbsp;` indentation** — the leading-whitespace strip on top-level paragraphs exists for the newline a bare-text parse turns into a space; it now uses `/^[\n\r\t ]+/`. Any strip that means "layout whitespace" has to spell the characters out rather than lean on `\s`.
- **A passthrough card is only byte-for-byte if its markup is stashed out of the way, not just shielded from the comment-strip regex** — `gutenbergPassthrough` content is swapped for a nonce placeholder alongside the unsupported wrappers, before the style-compaction and void-element passes run. Shielding it from the comment strip alone was not enough: ProseMirror's style re-serialization turned `style="color: red"` into `style="color:red"`, and the void-element pass turned `<img src="x">` into `<img src="x"/>`. Both are invisible to the block tripwire and both diff the post.
- **A `<li>` holding two or more paragraphs is left alone on purpose, even though core's rich-text `<li>` will flag it** — `toWordPressHTML` unwraps a single-child `<p>` inside an `<li>` (and a leading one before a nested list), but a genuinely multi-paragraph item keeps its `<p>` tags, because unwrapping would run the two paragraphs together and lose the break. Normal editing cannot produce the shape — Enter inside a list item makes a new list item, not a second paragraph — so it only arrives from a paste or from classic content that already had it, and a core-authored `<li>one<br>two</li>` round-trips byte-identically. Do not "fix" this by unwrapping; the test pinning it is `test-editor.js` `'multi-child <li> is left untouched'`.
- **ProseMirror re-serializes any `style` it renders, so a style Quill did not author must never reach it** — `renderSpec` does `a.style.cssText = value`, which parses the declaration into the CSSOM and writes it back normalized: `color:#cf2e2e` became `color:rgb(207, 46, 46)` in both WebKit and jsdom, and WebKit additionally moved the attribute to the end of the tag. Gutenberg compares the stored `style` against what `save()` regenerates from the comment attributes, so every coloured paragraph, heading, list and button was invalidated on the first edit. `replayRawAttrs` now emits a snapshot's `style` as `data-quill-style`; `toWordPressHTML` rebuilds the element's attribute list to rename it back, which keeps both the value and its position verbatim. A style the node itself renders still goes through the CSSOM and is still normalized by the compaction pass — that is correct, since Quill authored it. Anything else carrying a verbatim attribute value needs the same treatment.
- **Delimiter attributes must go through `serializeAttributes`, never `JSON.stringify`** — core escapes `--`, `<`, `>`, `&` and `\` so the JSON cannot terminate or corrupt the HTML comment that holds it. `delimiterAttrs` in `editor-transforms.js` is the single wrapper; all five save sites use it. Carried keys also keep the order WordPress gave them (`overlayCarried`), because spreading moved every key the node also computes to the end of the comment and diffed every post.
- **A regex over the final HTML string must treat `<` and `>` inside attribute values as data** — HTML serializers escape `&` and `"` in an attribute value but not `<` or `>`, so an `alt="a <b> tag"` is literal in the output. A naive `<img[^>]*>` ends the match inside the alt text and corrupts it (caught by the gallery suite's deliberately hostile alt strings). The void-element pass uses `(?:"[^"]*"|'[^']*'|[^>"'])*` to step over quoted values.
- **A node with its own node view never sees `renderHTML`, so a block setting can save correctly and still draw nothing** — `renderHTML` is only used for serialization once a node view exists; the canvas shows whatever the view builds. `ResizableImage` builds a `div.image-wrapper` from scratch, so `is-style-rounded` was in the saved markup, in the delimiter, and in the toolbar's active state while being absent from the editor DOM entirely — a block style that looked broken but tested green everywhere. `_applyAttrs` now copies the `is-style-*` token onto the wrapper. Any new setting on a node-view-backed node (image is the only one today) needs the same explicit copy.
- **A decoration that follows the caret cannot double as the display of a stored setting** — `_tabDecorations` marks the visibly active tab from `state.selection.head`, so `tabPanel.isDefaultTab` (stored as `activeTabIndex`) had nothing of its own on screen. It needs a second decoration keyed off the stored value — `is-default-tab` is the pattern, as is the accordion's `is-open` label. Same shape whenever an editor-only affordance and a publishing choice want the same visual slot: give the publishing choice a label, never the affordance.
- **A leaf block in `DELETABLE_BLOCKS` needs `_deletableTarget`, not the ancestor walk** — `_deletableBlockAt` climbs `$pos.depth`, which only ever finds a block the caret sits *inside*. A selected separator is a leaf: the node selection resolves before it, so the walk returns the doc and the ✕ never appeared. `_deletableTarget(state)` checks `selection.node` first and falls back to the walk; both the ✕ and ⌘⇧⌫ route through it. Esc / double-Enter deliberately still use the walk — there is no caret inside a leaf to exit from.
- **Every `#toolbar-row2` group must carry `class="tb-group"`, and an icon-only group `tb-group-icons` too** — the row's two metric rules key off those classes (`_buildSettingGroups` sets `tb-group` on each generated group). A static span added without the class gets neither rule and its buttons fall back to the 26px icon square, which reads visibly tighter than every text button beside it — how "New tab" shipped wrong. The audit snippet is in `docs/editor-preview-gaps.md`.
- **A widget decoration next to the caret makes WebKit drop every keystroke, and jsdom/Chromium never show it** — the empty-title placeholder on `accordionHeading`/`detailsSummary` started as a `Decoration.widget` holding a `contenteditable="false"` span. In the app the caret landed in the title correctly (verified by logging `editor.state.selection` and `document.getSelection()` out to Swift) and every character typed was silently discarded; the same code typed fine in Chromium and passed in jsdom. Draw placeholder text as generated content (`::before`/`::after`) keyed off a `Decoration.node` class instead — `is-untitled` is the pattern. The details status badge moved from `summary::after` to `.wp-block-details:not(.shows-content)::after` to free the pseudo-element.
- **An empty title inside `.wp-block-accordion-heading__toggle` is zero-width, so a click can never seat a caret in it** — the title span has no text and the absolutely-positioned hint adds no box, so the browser puts the caret in the panel paragraph below and an untitled accordion can never be named. `ContainerChrome`'s `mousedown` handler places it explicitly, but only from a `setTimeout` and without `preventDefault`: preventing the default leaves WebKit with nothing focused and the keystrokes go nowhere, and seating the selection synchronously is undone by WebKit's own click handling straight afterwards.
- **Gutenberg invalidates a block when the stored HTML carries anything its `save()` would not regenerate** — validation re-runs `save()` from the delimiter attributes and compares tokens. Class *order* and empty-valued attributes (`alt=""`) are ignored, but an extra attribute or an extra class is fatal: "Block contains unexpected or invalid content." Three image cases hit this before 2026-09-13 — a WP-resized image whose `style` Quill dropped while leaving `is-resized` on the figure, a Quill-resized image emitting `width`/`height` attributes core stopped writing years ago, and a decorative image keeping `role="none"` without the `isDecorative` attr. `applyImageDimensions` and `imageBlockAttrs` in `editor-transforms.js` now rebuild markup and attrs together; any future image presentation feature must add both halves.
- **Known unfixed edge case: non-dimension `style` properties on an image are dropped** — Quill models only `width`/`height`, so core's `aspect-ratio`, `object-fit`, `object-position` and border/shadow styles (and their `aspectRatio`/`scale`/`focalPoint`/border comment attrs) are lost on the first edit, which invalidates the block the same way. Unlike the container blocks, `core/image` has no `block-descriptors.js` entry, so it gets none of the `data-quill-block-attrs` carrying that would fix this generically; moving it onto the descriptor path is the real fix.
- **Check Gutenberg's own `save.jsx` before treating a block attribute as editor-only** — `core/details` renders `open={showContent}`, so `open` is genuine `post_content` and stripping it collapses every published details block on the front end; `core/accordion` saves nothing for `autoclose`, so that one really is Quill-internal (`data-autoclose`) and must be stripped on save. Verified 2026-09-12 against trunk, after the Phase 6 plan asserted both were editor-only. Fetch with `gh api search/code` — the block files are `.jsx`, so guessing `raw.githubusercontent.com/.../save.js` 404s.
- **Comment-only block attributes ride through Tiptap on `data-quill-block-attrs`, and `descriptor.ownedAttrs` is what lets a node turn one off** — WordPress keeps attributes like `autoclose` only in the delimiter comment, which ProseMirror's DOM parser cannot see, so the whole attribute object is carried on the element and re-emitted. The carrier alone cannot express deletion: `attrsFrom` returning `{}` is indistinguishable from "this block has no such attribute", so a value the user switched off kept its old setting. `ownedAttrs` names the keys whose absence is meaningful. Only declare a key the node genuinely reads back — an owned key with no round-trip behind it is deleted on the first edit — and never let `columnBlock` own `width`, since Quill has no width UI and the carried value is the only copy.
- **`gutenbergPassthrough` must opt out of modeled figures by class, not by excluding `<figure>` wholesale** — the parse rule was originally the single selector `[class*="wp-block-"]:not(figure)`, on the assumption that Quill's own rules "already own or transparently pass through" every `wp-block-*` figure. Only four do (`QUILL_MODELED_FIGURE_CLASSES` in `editor-transforms.js`: image, gallery, embed, table). Everything else fell through to the generic parser and was destroyed on the next save — verified 2026-08-19 in jsdom against the real `editor.html`: `figure.wp-block-audio` collapsed to a bare `<p>` holding only its caption text (the `<audio>` element gone), `figure.wp-block-video` to an empty `<p>`, `figure.wp-block-pullquote` was silently rewritten as a `blockquote.wp-block-quote`, and WP 7.1's new `figure.wp-block-playlist` lost its wrapper, its `wp:playlist` comments, and its `<figcaption>`. Fixed by adding a second, figure-only parse rule that defers via `isModeledFigure(el)` and otherwise hands off to `parsePassthroughBlock`. Consequence to keep in mind: a *new* figure-rooted block Quill decides to model natively must be added to `QUILL_MODELED_FIGURE_CLASSES`, or passthrough (priority 200) will out-rank its own rule and swallow it. Regression tests: `Scripts/test-editor-passthrough.js`, both the figure-rooted describe block and the modeled-figure guards.
- **A `describe()` whose first test calls `setContent` right after a block that leaves the doc as a single atom node needs a throwaway `setContent('<p></p>', false)` in `before()`** — the same one-shot jsdom/Tiptap quirk already documented in the root `CLAUDE.md` for `extendMarkRange`. Confirmed 2026-08-19 to reproduce on unmodified `editor.html`, so it is a harness artifact, not a code bug; two of the new passthrough/keyboard describe blocks carry the hook for exactly this reason.
- **ProseMirror's two clipboard branches have separate hooks, and `handlePaste` runs *after* the parse, not before** — verified 2026-08-08 by reading `parseFromClipboard` in `tiptap-bundle.js`. The paste handler calls `parseFromClipboard(...)` first to build a slice, then `someProp("handlePaste", fn => fn(view, event, slice))` — so `handlePaste` receives an already-parsed slice and cannot pre-empt `transformPastedHTML`. Inside `parseFromClipboard` the branch is `!!text && (plain || parentIsCode || !html)`: with a `text/html` flavor present it runs `transformPastedHTML`; with **text only** it runs `transformPastedText` and then splits on `/(?:\r\n?|\n)+/` into one `<p>` per line, never touching `transformPastedHTML`. That asymmetry was a live bug — the footnote flatten guard existed only on the HTML hook, so multi-line plain text pasted into a footnote (`footnoteItem` is `inline*`) put line 1 in the entry and dropped the rest *after* the footnotes list as sibling paragraphs. Fixed in the `transformPastedText` hook directly above `transformPastedHTML`; both are gated on `_isInFootnote()` and must stay in sync. Code blocks need no guard — `parseFromClipboard` checks `$context.parent.type.spec.code` and inserts raw text before either hook's result is used. Regression tests: `Scripts/test-editor-paste.js`.
- **Anything that inserts generated HTML must strip inter-block whitespace text nodes AND pass `parseOptions: { preserveWhitespace: false }`** — both, not either. ProseMirror wraps the first `\n` between block tags in a blank paragraph even with `preserveWhitespace: false`. This bit the AI-insert path first and then `window.insertMarkdown` (marked emits `\n` between blocks); both now do the same `Array.from(tmp.childNodes).filter(TEXT_NODE && !textContent.trim()).remove()` pass before inserting. `insertMarkdown` additionally trims marked's trailing newline inside `pre > code`, which would otherwise show as an empty last line in every pasted code block.
- **Any new `toWordPressHTML` pass is a whole-tree `div.querySelectorAll(...)` and will reach into `gutenbergPassthrough` subtrees unless explicitly shielded** — `gutenbergPassthrough` elements are stashed out into placeholder divs at the very top of `toWordPressHTML` (before any transform runs) and only spliced back in — completely untouched — right before the final `wp:name` comment-regeneration pass, after every other pass (comment-strip, media-id class, image/heading/list/blockquote/cite/table/footnote/embed/gallery normalization) has already run. This is deliberately a *wide* shielding window, not scoped to just the comment-strip regex: an earlier implementation spliced passthrough elements back in immediately after the comment-strip alone, which left them exposed to the later heading-class/empty-cite-removal/empty-figcaption-removal passes — a nested `<h3>` silently gained `wp-block-heading`, and intentionally-empty `<cite>`/`<figcaption>` elements were deleted, even though the whole point of passthrough is byte-for-byte preservation. If you add a new unconditional `div.querySelectorAll(...)` pass to `toWordPressHTML`, it automatically inherits this protection as long as it's placed between the stash and the splice-back — do not add passes after the splice-back point without auditing whether they should reach into passthrough content.
- **`formatHTML`'s `BLOCK` set changes affect ALL existing content wrapped in that tag, not just the new case motivating the change** — adding `'div'` to `BLOCK` (for `gutenbergPassthrough`'s nested divs to indent in code view) also changed formatting of the pre-existing `EmbedBlock` wrapper (`<div class="wp-block-embed__wrapper">`), whose only child is a text node with a literal `'\n'+url+'\n'` (an intentional raw-newline design, not element children). Without handling this, the div's opening tag got indented but the raw-newline text pushed the URL and closing `</div>` onto unindented lines below it. Fixed by trimming a block tag's inner text when it has no element children at all (`serialize`'s `isTextOnly` check). When adding a tag to `BLOCK`, grep for every existing `renderHTML` that emits that tag and check its actual child-node shape (text vs. element children), not just the new feature's fixture.
- **Gap-cursor styling, not doc-model surgery, for the caret next to atomic block nodes** — `galleryBlock`/`embedBlock` are `atom: true, group: 'block'` with no content, so a caret position next to one (before, after, or between two of them — anywhere, not just doc-end) has no adjacent inline content to sit in. Tiptap's built-in `gapCursor` extension (enabled by default via `StarterKit`, never disabled here) already handles this correctly — it's a real ProseMirror `Decoration.widget` at the exact position, and typing into it works out of the box (inserts a paragraph there automatically). The only actual problem was cosmetic: its default widget is a black horizontal bar (`.ProseMirror-gapcursor:after { border-top: 1px solid black }`, injected into `<head>` by the Tiptap bundle at runtime), which looks broken next to the app's blue vertical `caret-color: #007aff`. Fixed with a pure CSS override in `editor.html` (near the `.ProseMirror { caret-color }` rule) that redraws the widget as a vertical `border-left` bar in the same blue — scoped under `.ProseMirror .ProseMirror-gapcursor:after` so its higher specificity reliably beats the later-injected default regardless of DOM order. An earlier attempt patched this by forcing a trailing paragraph into the document (`appendTransaction`) and then stripping it back out in `toWordPressHTML` before save — don't do that: it only covered the doc-end case, left the same bug everywhere else an atom neighbors a gap, and permanently added a "insert fake HTML, then remember to remove it" liability to the save path for a rendering-only problem.
- **`marked` is a second, separate IIFE bundle — kept out of `bundle-tiptap.sh` so regenerating it can't drift the editor onto a newer Tiptap** — `marked-bundle.js` (`window.MarkedBundle`, ~40 KB) is generated by `./Scripts/bundle-marked.sh` and loaded by its own `<script src>` in `editor.html` between the Tiptap bundle and `editor-transforms.js`. Only `window.insertMarkdown` consumes it. Kept out of `bundle-tiptap.sh` on purpose so regenerating a Markdown parser can't drift the editor onto a newer Tiptap 2.x.
- **Tiptap is bundled locally as IIFE — `type="module"`/ES `import` silently fails under `file://` in WKWebView and `editorReady` never fires** — `Sources/QuillKit/Resources/tiptap-bundle.js` is a minified IIFE bundle (`window.TiptapBundle`) generated by `./Scripts/bundle-tiptap.sh` (requires `node`). No CDN requests at runtime; editor loads instantly from disk. IIFE format is required — `type="module"` + ES module `import` statements do NOT work with `file://` URLs in WKWebView (silent failure, `editorReady` never fires). `editor.html` loads the bundle via `<script src="./tiptap-bundle.js">` and destructures from `TiptapBundle`. To update Tiptap 2.x: re-run the script and rebuild. To upgrade to Tiptap 3.x: bump `"^2"` → `"^3"` in the script's package.json block, verify exports in `entry.js` still exist, and check for API changes in `editor.html`.
- **Known unfixed edge case: `galleryBlock.sizeSlug` is per-gallery, not per-image** — `GallerySheet`'s Size picker applies one slug to every image in the gallery, and `parseHTML`'s `getAttrs` derives `node.attrs.sizeSlug` from only `imageFigures[0]`'s class, discarding size info for images 2..n in a *loaded* gallery with heterogeneous per-image sizes (real WordPress galleries can have these). This is currently harmless — a loaded gallery's `sourceHTML` renders verbatim, so `attrs.sizeSlug` is never read back for that case — but it's lossy ground truth that the next feature to trust it (e.g. an edit-existing-gallery flow, implied by v1's insert-only scoping) would need to fix first, by moving size onto each `images[]` entry instead of the node. Deliberately left unfixed as of 2026-07-09 since v1 has no gallery-editing UI to expose the gap.
- **Known unfixed edge case: image link toggle collapses all WordPress link destinations to "media"** — `ResizableImage.linkTo`/`linkHref` only models "linked to full image" vs. "not linked"; any `<a>` wrapping the image (attachment-page link, custom URL, or a true full-image link) is detected as `linkTo: 'media'` on load, since detection just checks for a non-empty `href`. A passive load→save round-trip is lossless (the original `href` is preserved verbatim), but toggling the link off then back on replaces the original destination with the image's own full-resolution URL, since there's no attribute tracking the original destination *type*. Deliberately left unfixed as of 2026-07-10 — a real fix means modeling WordPress's actual `linkDestination` enum (`attachment`/`custom`/`media`/`none`), a larger schema change than the surrounding bug-fix pass warranted.
- **Known unfixed edge case: `AIResultPanel`/`beginAIOperation` reentrancy** — `beginAIOperation()` in `editor.html` unconditionally overwrites the module-level `_aiFrom`/`_aiTo`/`_aiOriginalHTML` globals with no guard against a prior operation still being in flight (`_aiInProgress` isn't checked). If the user selects different text and triggers a second right-click AI operation before the first one's Claude response returns and its `AIResultPanel` appears, the second call's globals clobber the first's, and `AIResultPanel.show()`'s existing monitor-dedup fix (below) only prevents the resulting double keypress-handler firing — it does not stop the first operation's `onAccept`/`onDiscard` callbacks from being silently overwritten and orphaned. Never confirmed in practice; a real fix needs `beginAIOperation()` to reject (or queue) a second call while `_aiInProgress` is true. Deliberately left unfixed as of 2026-07-05 pending a discussion of the UX tradeoff (reject vs. queue vs. auto-discard the first).
- **Cmd+click opens links, and fragment-only `href`s must be skipped or footnote markers resolve to a blocked `file://` URL** — `handleClick` in `editorProps` checks `event.metaKey`, walks up the DOM to find an `<a>` element, and posts its `href` to the `openLink` Swift message handler. Fragment-only hrefs (`#...`) are skipped via `el.getAttribute('href').startsWith('#')` — without this, footnote marker `<a href="#UUID">` elements resolve to `file:///...#UUID` (truthy), which `isAllowedExternalURL` blocks, but `handleClick` returns `true` and swallows the click. The `body.cmd-held` CSS class (toggled by keydown/keyup/blur) adds `cursor: pointer` and `text-decoration: underline` to links while Cmd is held.
- **`ResizableImage` must import `Image` as a named import, or the default export shadows the name** — `Image` from `@tiptap/extension-image@2` must be imported as a named import (`{ Image as TiptapImage }`) so the default export doesn't shadow the name. `ResizableImage` extends `TiptapImage` and adds `width`, `height`, `mediaId` attributes. It parses standard `<img width="..." height="...">` and `class="wp-image-{id}"` on load; serializes to `width="..."`, `height="..."`, `data-media-id="..."` on output.
- **`ImageNodeView` is a plain JS class, not a React/Svelte component** — registered via `addNodeView()` returning `new ImageNodeView(node, editor, getPos)`. Implements the ProseMirror NodeView interface: `dom`, `update()`, `selectNode()`, `deselectNode()`, `destroy()`, `stopEvent()`, `ignoreMutation()`. `stopEvent` returns `true` for `mousedown` on `.resize-handle` elements so ProseMirror doesn't steal the event.
- **`.image-frame` wraps only the `<img>` and handles, so handles align to the image rather than to the wrapper's caption height** — `ImageNodeView` creates an inner `.image-frame` div (child of `.image-wrapper`, sibling of `<figcaption>`) that wraps only the `<img>` and the four `.resize-handle` elements. All handle CSS positions are relative to `.image-frame`, so handles align to the image dimensions, not the full wrapper including caption height. `.image-frame { position: relative; display: inline-block; line-height: 0; }`. Do not put handles directly inside `.image-wrapper`.
- **Non-leaf NodeView + NodeSelection: must intercept `stopEvent`** — because `ResizableImage` has `content: 'inline*'` with `contentDOM = figcaption`, ProseMirror maps any click inside the `dom` wrapper to a text cursor inside `contentDOM` rather than creating a NodeSelection. This means `selectNode()` is never called, so the blue outline, resize handles, and image toolbar never appear. Fix: in `stopEvent()`, intercept `mousedown` where `!this.figcaption.contains(e.target)`, call `e.preventDefault()`, dispatch `this.editor.commands.setNodeSelection(pos)`, and return `true`. Without this, clicking an image does nothing visible.
- **`window.insertImage` must move the cursor off the caption after `setImage`** — Tiptap's `setImage` leaves the selection inside the new figure's empty `<figcaption>` (a consequence of `ResizableImage`'s `content: 'inline*'` + `contentDOM = figcaption`), so typing straight after an insert silently wrote caption text instead of body text. `insertImage` now resolves the image's depth via `_ancestorDepth($from, 'image')`, inserts a `paragraph` at `$from.after(imgDepth)` and selects it. The caption is deliberately left untouched and still clickable, so captioning stays opt-in. Two consequences to keep in mind: saved content gains an empty `<p></p>` after each image block (intended, and WordPress tolerates it), and because the paragraph is inserted *after* the image's own container depth the insert stays scoped inside a list item / blockquote / table cell rather than breaking out of it. All three insert paths (toolbar, post-upload, Finder drop) route through this one function. Regression tests: `Scripts/test-editor-keyboard.js` `'window.insertImage cursor placement'` (14 tests).
- **`ResizableImage` has `content: 'inline*'` for captions** — the image node is no longer atomic (leaf). `ImageNodeView` exposes `contentDOM = this.figcaption` so ProseMirror manages caption text directly inside the `<figcaption>`. `ignoreMutation` returns `false` for mutations inside `contentDOM` (so ProseMirror tracks caption edits) and `true` for all other mutations (resize handles, wrapper). `renderHTML` outputs `['figure', {}, ['img', HTMLAttributes], ['figcaption', 0]]` — the `0` is the ProseMirror content hole. `parseHTML` has `contentElement: 'figcaption'` on the `figure.wp-block-image` rule so existing WordPress captions load correctly.
- **Tiptap node attrs: a per-attribute `parseHTML` stub must return `null`/`undefined` to be a true no-op, not a literal default value** — Tiptap's schema builder runs every attribute's own `parseHTML(el)` extractor *after* a parse rule's `getAttrs(el)` and merges the result on top, overriding any key it returns a non-null/non-undefined value for. `figureClass`/`figureId` on `ResizableImage` stub `parseHTML: () => null` (filtered out of the merge, so `getAttrs`'s computed value survives); `linkTo` was initially stubbed `parseHTML: () => 'none'` (matching its schema default, to keep the bare `img[src]` fallback rule sane) — but since `'none'` is non-null, it silently overwrote the *correct* `'media'`/`'none'` computed by the `figure.wp-block-image` rule's own `getAttrs` on every single parse. Fix: stub dead attrs with `parseHTML: () => null` always, regardless of the attribute's own default — let the ProseMirror schema `default` fill in genuinely-unset values instead.
- **`ResizableImage`'s per-attribute `parseHTML` can double as a fallback for parse rules with no `getAttrs` of their own** — `linkTo`/`linkHref` no longer use the dead-stub pattern above; their own `parseHTML(el)` actively detects an `<a>` wrapper (checking `el.tagName === 'FIGURE'` first to locate the real `<img>`, since `el` is whatever element the *matching rule* matched). This makes them work for both the `figure.wp-block-image` rule (which also computes the same value via its own `getAttrs`, redundant but consistent) **and** the bare `img[src]` fallback rule (used for classic/pre-Gutenberg linked images with no figure wrapper), which has no `getAttrs` at all. Before this, classic linked images silently lost their link on the first save in Quill. If you add a new attribute that must work under a rule without `getAttrs`, give it real per-attribute `parseHTML` logic rather than a `() => null` stub.

- **AI buttons are in the Tiptap toolbar, not the SwiftUI toolbar** — `btn-generate` (pencil SVG) and `btn-evaluate` (checkmark-circle SVG) live in `#ai-toolbar-group` in `editor.html`. `window.setAIEnabled(bool)` shows/hides the group; `window.setEvaluating(bool)` disables/enables the evaluate button during a run; `window.setEvaluationPanelOpen(bool)` toggles the `.active` class on the evaluate button. - **`showAIResult` inserts at block-node boundaries, not text positions** — using `setTextSelection({ from, to }).insertContent(html)` with character positions inside a paragraph causes ProseMirror to split the paragraph at those points, leaving empty `<p>` fragments before and after the inserted content. Instead, expand to node boundaries: `$from.before($from.depth)` / `$to.after($to.depth)`, then call `insertContentAt({ from: nodeFrom, to: nodeTo }, html, { parseOptions: { preserveWhitespace: false } })`. The `preserveWhitespace: false` option is required — the default `'full'` causes ProseMirror to wrap the `\n` characters Claude emits between `<p>` tags into blank paragraph nodes. For container operations (lists/tables), `showAIResult(html, cFrom, cTo)` re-derives container boundaries from `_aiFrom` after restoring the original document — saved positions shift during the `getHTML`/`setContent` round-trip for tables. - **AI operations detect list/table context** — `beginAIOperation()` walks `$from.depth` to detect parent `bulletList`, `orderedList`, or `table` nodes. When found, it sends the full container text to Claude with context-specific prompts (via `AIPromptBuilder.operationPrompt(context:)`) and returns `containerFrom`/`containerTo` so `showAIResult` can replace the whole container. The context menu's ancestor walk in `DroppableWebView.rightMouseDown` requires `sel.from !== sel.to` to prevent a collapsed cursor (click with no selection) from triggering AI operations on an entire table/list.
- **Strip inter-block whitespace text nodes before inserting AI HTML** — even with `preserveWhitespace: false`, ProseMirror can create a blank paragraph from the first whitespace text node at the start of a slice. Before calling `insertContentAt`, parse the HTML through a temporary `div`, remove whitespace-only `childNodes` (text nodes between block elements), and use the resulting `innerHTML`. This ensures zero inter-paragraph whitespace reaches ProseMirror's parser.
