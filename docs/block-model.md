# Quill — the Gutenberg block model

How Quill models, carries and preserves Gutenberg blocks. Referenced from the root `CLAUDE.md`.

- **Adding a block setting is one line in `block-settings.js`** — the registry names how each Gutenberg setting draws (`carried`, `flagClass`, `valueClass`, `style`, `attr`), and the machinery derives the Tiptap attribute (`withBlockSettings` in `editor.html`), the delimiter key (`attrsFromSettings`/`ownedAttrsFor` in `block-descriptors.js`) and the toolbar control (`_buildSettingControl`) from it. A `control` field adds the toolbar control; `propagate: '<node>'` also writes the value to every descendant of that type in the same transaction, which is what core's twice-stored accordion icon settings need. Never write a `sourced` setting to the delimiter — WordPress reads those back out of the markup. Two settings the registry cannot express are document structure, not settings, and stay hand-written: a table's `<thead>`/`<tfoot>` sections (`tableRow.rowType`) and its caption's attachment to the figure.
- **An attribute no block setting names is carried anyway** — every node wrapped by `withBlockAttrs` snapshots its element's attributes on load (`withRawAttrs` in `editor.html`) and replays them on save in the source's own order, with the node's own values winning. That is what keeps columns' `is-not-stacked-on-mobile`, a details `name` and an ordered list's `reversed` after an edit, none of which has a registry entry. Two lists bound it: `RAW_ATTRS_MODELED` names the attributes a node draws itself, which must never be replayed or a value the user just turned off comes back — a node whose class any setting writes lists `class` there; `RAW_ATTRS_EXEMPT` holds the four figure blocks, which rebuild their figure from modelled attributes instead. A setting that draws a *child element* still needs a registry entry.
- **Unsupported block preservation — one path, not two** — on load, `window.setContent` (and `_exitCodeView`'s user-edited branch) run `post_content` through `wrapUnsupportedBlocks`, which uses Quill's `parseBlocks` (`block-parser.js`) to enumerate top-level blocks, cuts each one's source by offset, and replaces **every block Quill has no node for** with a `div.wp-block-quill-unsupported` carrying its exact source; `toWordPressHTML` swaps each wrapper back for those bytes verbatim on save. The rule is simply `!!blockName && !modelsBlockName(blockName)`, plus a guard that a modeled name saving no markup is wrapped too. Covers Cover, Media & Text, Spacer, Custom HTML, shortcodes, the self-closing dynamic blocks, page breaks, Read More, and any third-party block. HTML outside any block (a freeform slice) gets the same wrapper per element, the way Gutenberg's Convert to Blocks treats it: `wrapFreeformHTML` keeps each top-level element Quill would lose as a `core/html` block (`<!-- wp:html -->` around its `outerHTML`, so equivalent markup rather than the original bytes), searching through grouping tags (`div`, `section`, …) that carry no attributes, since unwrapping those changes nothing on the page. Prose and inline tags (`FREEFORM_PROSE_TAGS`) and anything with a `wp-block-*` class are left to the editor's own rules, and a slice with nothing to keep is returned untouched. The class-based `gutenbergPassthrough` card is what is left of the old path: it now only holds an unmodeled block *nested inside* a modeled container, where there is no top-level slice to wrap. `_reportBlocksAtRisk` separately counts every block name in the source tree — at every depth, per instance — against the same count taken from the document, and posts `blocksAtRisk` to Swift, which shows `BlockRiskAlarm`'s banner and refuses to save (and suspends autosave) until acknowledged. Spec: `docs/superpowers/specs/2026-09-12-unsupported-block-preservation-design.md`.
- **A Group opens only when Quill models everything in it** — `groupBlock` (`editor.html`) is a container like `columnBlock`, parsing the seven tags `groupTags()` lists (`div`, `section`, `header`, `footer`, `main`, `aside`, `article`) with the `wp-block-group` class and rendering the tag it parsed; any tag but `div` is written as `tagName`. `blockNeedsWrapping` wraps a top-level block whole when any Group in its tree fails `groupFullySupported`: the Group must hold at least one block (an empty one would gain a paragraph); every block inside it, at every depth, must be one Quill models and must save markup; and its own markup with the inner blocks cut out (the parser's `innerHTML`) must be one bare wrapper element of a parsed tag, with only whitespace beside and inside it (this rejects `nav`, the old `wp-block-group__inner-container`, and stray text or elements), no attribute the carrier would drop (`on*`, `data-quill-*`), and a delimiter `tagName` that matches the element (absent for `div`), since a save writes `tagName` from the element. A Group's `anchor` and `className` go through the same delimiter repair as every modeled block: a hand-written Group whose comment lacks them gains them on edit. So a Columns holding a failing Group is locked whole rather than editable around a card: it loses editability, never content, and keeps every Group on the byte-exact path. The label (Row for `flex`, Stack for vertical `flex`, Grid, else Group, followed by `: ` and the custom name when there is one) is drawn by `GroupNodeView` outside `contentDOM`; colours, padding and Row/Grid layout are not drawn. The node claims a loaded element only when it carries its own `wp:group` comment (`_opensGroup` in `editor.html`), because only delimited Groups pass the load check; a `wp-block-group` element with no comment (a classic post, Code View, AI output) stays a class-only card as it always was, or its unmodeled children (a `<video>`, an `<iframe>`) would be dropped on the first edit. A paste is the exception (`_parsingPaste`, set in `transformPastedHTML`): outside HTML has been reduced by `cleanPastedHTML` and Quill's own copy holds only what the node held, though a copied card (`data-quill-passthrough`) stays a card. A `nav` or any other tag the node does not parse also stays a card. Spec: `docs/superpowers/specs/2026-10-12-group-block-and-locked-cards-design.md`.
- **A locked card is one row: its type, its custom name, and a pointer to Code View** — every card, top-level or nested, is labelled with the block type, followed by `: ` and the block's `metadata.name` when that is a non-empty string (`cardLabel`, so `Cover: Membership hero`); a Group's label follows the same rule (`groupLabel`, `Group: Hero`). A locked card shows none of the text inside the block, because text in a card looked editable beside an editable Group; it is drawn as one row, the label on the left and `Edit in Code View (</>)` on the right. Custom HTML and Shortcode cards are the exception: their markup is their content, so they keep a monospaced preview of their source (`_peekText`) and draw as a taller card (`.passthrough-card.has-peek`).
- **A synced pattern's card is filled from WordPress, outside the document** — a top-level card whose source is one `core/block` whose `ref` is a positive safe integer. After `setContent` and `_exitCodeView`'s user-edited branch, the editor posts `requestSyncedPatterns({ generation, refs })` with each ref once; `EditorCoordinator` hands the whole list to `onRequestSyncedPatterns` (`WordPressClient.fetchSyncedPatterns`, `GET /wp/v2/blocks?include=…&status=publish&_fields=id,title,content.protected`, one request per 100 refs, in view context: the blocks controller exposes `title.raw` there, and edit context silently drops every pattern the user can't edit) and answers `window.setSyncedPattern(generation, ref, result)` for every ref with `{ title }`, `{ notFound: true }` or `{ failed: true }`. Not found means what WordPress's `render_block_core_block` means: the ref is missing from the published-only response (draft, private, trashed or deleted), or `content.protected` is true (WordPress's `(bool) post_password`, which agrees with the renderer's `empty()` on a password of `"0"`); either way the front end renders nothing. Any error fails every ref in the request. Only the title is fetched; the card shows none of the pattern's content. Results live in a `Map` keyed by ref and are drawn by the node views registered for that ref, so a result never dispatches a transaction: no edit, no undo step, no change to what is saved. A result for a ref this load asked for is kept even while no card shows it, so a card deleted mid-fetch comes back loaded on undo; a result whose generation is not the current load's, or for a ref never asked for, is dropped, and the map is cleared (and every card redrawn as loading) *before* each load, because ProseMirror can reuse an identical card's view across loads. A card created after the load (a paste) requests any ref not yet asked for this load, batched in a microtask. Swift decodes HTML entities in the raw title. Edit in WordPress posts `openSyncedPattern({ ref })`; Swift builds `{site}/wp-admin/post.php?post={ref}&action=edit` and opens it only through `isAllowedExternalURL`. A synced pattern nested in a container gets no fetch: inside a Group it locks the Group, inside Columns it follows the class path.
- **`parseBlocks` is held to WordPress's parser, not to the spec** — `block-parser.js` is Quill's own reader of block comments (written without WordPress's GPL source); `Scripts/test-block-parser.js` compares its tree with `@wordpress/block-serialization-default-parser`, a test-only dependency, and that comparison is the authority. Design: `docs/superpowers/specs/2026-09-25-block-parser-rewrite-design.md`. Four rules were measured against WordPress after the spec was written and are not in it: a stray closing comment at the top level starts a freeform block at the end of the previous block, so top-level text before it joins that block; a closing comment ending in `/-->` is self-closing; a *nested* block closed with nothing since its last inner token records `""` in `innerContent` (a top-level one records nothing); and the attribute text is JSON-parsed together with the whitespace after `}`, so a no-break space, form feed or U+2028 there gives `attrs: null`. The one deliberate difference: two or more blocks open at the end of the input nest instead of repeating the inner text, and `blockSourceSlices` appends their missing closing comments.
- `gutenbergPassthrough` Tiptap node (`editor.html`) — two parse rules feed it. `div.wp-block-quill-unsupported` is the wrapper every unmodeled *top-level* block now arrives in, and is byte-exact. The `[class*="wp-block-"]` catch-all is the fallback for an unmodeled block *nested inside* a modeled container; it preserves `outerHTML` but not inter-element whitespace, because Tiptap strips that before any parse rule runs. Both render the same static one-row card pointing to Code View, except a top-level card whose source is one `core/html` block (`customHTMLBlock`), which reads "Renders as Custom HTML in WordPress · Edit…" and opens `CustomHTMLSheet` on Edit… or double-click (`window.editCustomHTML` → `customHTML` message → `window.insertCustomHTML`). The sheet edits the text between the delimiters, sliced from the source rather than the parser's `innerHTML`, which drops nested blocks, and the replace keeps the original opening comment byte for byte. The sheet splits the content into HTML, CSS and JavaScript tabs the way Gutenberg's `parseContent` does (`CustomHTMLParts`: a `<style data-wp-block-html="css">` and a `<script data-wp-block-html="js">`, matched as exact text and only where Gutenberg writes them, ahead of the HTML, so a commented-out marker is never revived and content without them stays byte for byte) and shows the CSS/JS tabs only when `users/me` reports `unfiltered_html` (`AppState.canPostUnfilteredHTML`, asked once per connection) or the block already holds CSS or JS. The insert menu's Custom HTML item uses the same path; a caret inside a container inserts after its top-level block, since a nested `core/html` has no card on reload. Spec: `docs/superpowers/specs/2026-10-05-custom-html-block-design.md`. See `docs/superpowers/specs/2026-07-12-gutenberg-passthrough-block-design.md` and the `toWordPressHTML` gotcha above about its shielding window.
