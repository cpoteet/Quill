# Editor resources (editor.html / editor-transforms.js / tiptap-bundle.js)

Implementation gotchas specific to this directory, split out from the project root `CLAUDE.md` (2026-07-11) to keep the root file lazy-loaded. See the root `CLAUDE.md` for architecture, build/test commands, and cross-cutting conventions.

## Gutenberg HTML output reference

### What each element currently outputs (as of 2026-06-11)

| Tiptap internal | `toWordPressHTML()` output |
|---|---|
| `<h1>`–`<h6>` | `+ class="wp-block-heading"` |
| `<ul>` | `+ class="wp-block-list"`; a leading `<p>` inside `<li>` unwrapped to a text node when it is the item's only child **or** when every following sibling is a nested `<ul>`/`<ol>` (matching Gutenberg's `<li>text<ul>…`); items with a second paragraph are left alone |
| `<ol>` | `+ class="wp-block-list"`; a leading `<p>` inside `<li>` unwrapped to a text node when it is the item's only child **or** when every following sibling is a nested `<ul>`/`<ol>` (matching Gutenberg's `<li>text<ul>…`); items with a second paragraph are left alone |
| `<blockquote>` | `+ class="wp-block-quote"` |
| `<pre>` | `+ class="wp-block-code"` |
| `<hr>` | `+ class="wp-block-separator has-alpha-channel-opacity"` |
| `<figure><img class="alignXXX"><figcaption>…</figcaption></figure>` (Tiptap `renderHTML` output) | figure gets `class="wp-block-image alignXXX"`; alignment class moved from `img` to `figure`; `class="wp-image-{id}"` added to `img` when `data-media-id` is set; non-empty `<figcaption>` gets `class="wp-element-caption"`; empty figcaption removed |
| `<table>` | Tiptap artifacts stripped (`style`, `<colgroup>`, default `colspan="1"`/`rowspan="1"`, single-`<p>` cell unwrap); wrapped in `<figure class="wp-block-table">`; first all-`<th>` row promoted from `<tbody>` to `<thead>` |
| `<figure class="wp-block-embed">` (EmbedBlock node) | passes through unchanged — classes emitted by `renderHTML` via `embedClassFor()` |
| Footnote marker `<sup data-fn class="fn">` | anchor text renumbered 1..n in document order by `toWordPressHTML` |
| `<ol class="wp-block-footnotes">` | excluded from `wp-block-list`; passes through unchanged |
| `<figure class="wp-block-gallery">` (galleryBlock node, atomic) | wrapped with `<!-- wp:gallery {ids,columns,linkTo[,imageCrop]} -->`/`<!-- wp:image {[id,]sizeSlug,linkDestination} -->` comments; existing galleries round-trip via a verbatim `sourceHTML` attr (captures anything the structured attrs don't model), not reconstructed — same pattern as `EmbedBlock`. Per-image `caption` **is** modeled: emitted on the reconstruction path as `figcaption.wp-element-caption` via `textContent` (never `innerHTML` — the text comes straight from a `TextField`), omitted when empty, and read back on parse — unlike `sizeSlug`, see its known-edge-case bullet below |
| Any other `wp-block-*` classed, non-`<figure>` element with no dedicated parse rule (gutenbergPassthrough node, atomic) | passes through byte-for-byte via a verbatim `sourceHTML` attr — never reconstructed, never descended into. If adjacent `<!-- wp:name -->`/`<!-- /wp:name -->` comments were present on load, fresh ones are regenerated around it on save; class-only markup (no original comments) gets none added |
| Bold, italic, strike, inline code, links, paragraphs | unchanged — already match Gutenberg |



## Known gotchas

- **ProseMirror's two clipboard branches have separate hooks, and `handlePaste` runs *after* the parse, not before** — verified 2026-08-08 by reading `parseFromClipboard` in `tiptap-bundle.js`. The paste handler calls `parseFromClipboard(...)` first to build a slice, then `someProp("handlePaste", fn => fn(view, event, slice))` — so `handlePaste` receives an already-parsed slice and cannot pre-empt `transformPastedHTML`. Inside `parseFromClipboard` the branch is `!!text && (plain || parentIsCode || !html)`: with a `text/html` flavor present it runs `transformPastedHTML`; with **text only** it runs `transformPastedText` and then splits on `/(?:\r\n?|\n)+/` into one `<p>` per line, never touching `transformPastedHTML`. That asymmetry was a live bug — the footnote flatten guard existed only on the HTML hook, so multi-line plain text pasted into a footnote (`footnoteItem` is `inline*`) put line 1 in the entry and dropped the rest *after* the footnotes list as sibling paragraphs. Fixed in the `transformPastedText` hook directly above `transformPastedHTML`; both are gated on `_isInFootnote()` and must stay in sync. Code blocks need no guard — `parseFromClipboard` checks `$context.parent.type.spec.code` and inserts raw text before either hook's result is used. Regression tests: `Scripts/test-editor-paste.js`.
- **Anything that inserts generated HTML must strip inter-block whitespace text nodes AND pass `parseOptions: { preserveWhitespace: false }`** — both, not either. ProseMirror wraps the first `\n` between block tags in a blank paragraph even with `preserveWhitespace: false`. This bit the AI-insert path first and then `window.insertMarkdown` (marked emits `\n` between blocks); both now do the same `Array.from(tmp.childNodes).filter(TEXT_NODE && !textContent.trim()).remove()` pass before inserting. `insertMarkdown` additionally trims marked's trailing newline inside `pre > code`, which would otherwise show as an empty last line in every pasted code block.

- **Any new `toWordPressHTML` pass is a whole-tree `div.querySelectorAll(...)` and will reach into `gutenbergPassthrough` subtrees unless explicitly shielded** — `gutenbergPassthrough` elements are stashed out into placeholder divs at the very top of `toWordPressHTML` (before any transform runs) and only spliced back in — completely untouched — right before the final `wp:name` comment-regeneration pass, after every other pass (comment-strip, media-id class, image/heading/list/blockquote/cite/table/footnote/embed/gallery normalization) has already run. This is deliberately a *wide* shielding window, not scoped to just the comment-strip regex: an earlier implementation spliced passthrough elements back in immediately after the comment-strip alone, which left them exposed to the later heading-class/empty-cite-removal/empty-figcaption-removal passes — a nested `<h3>` silently gained `wp-block-heading`, and intentionally-empty `<cite>`/`<figcaption>` elements were deleted, even though the whole point of passthrough is byte-for-byte preservation. If you add a new unconditional `div.querySelectorAll(...)` pass to `toWordPressHTML`, it automatically inherits this protection as long as it's placed between the stash and the splice-back — do not add passes after the splice-back point without auditing whether they should reach into passthrough content.
- **`formatHTML`'s `BLOCK` set changes affect ALL existing content wrapped in that tag, not just the new case motivating the change** — adding `'div'` to `BLOCK` (for `gutenbergPassthrough`'s nested divs to indent in code view) also changed formatting of the pre-existing `EmbedBlock` wrapper (`<div class="wp-block-embed__wrapper">`), whose only child is a text node with a literal `'\n'+url+'\n'` (an intentional raw-newline design, not element children). Without handling this, the div's opening tag got indented but the raw-newline text pushed the URL and closing `</div>` onto unindented lines below it. Fixed by trimming a block tag's inner text when it has no element children at all (`serialize`'s `isTextOnly` check). When adding a tag to `BLOCK`, grep for every existing `renderHTML` that emits that tag and check its actual child-node shape (text vs. element children), not just the new feature's fixture.

- **Gap-cursor styling, not doc-model surgery, for the caret next to atomic block nodes** — `galleryBlock`/`embedBlock` are `atom: true, group: 'block'` with no content, so a caret position next to one (before, after, or between two of them — anywhere, not just doc-end) has no adjacent inline content to sit in. Tiptap's built-in `gapCursor` extension (enabled by default via `StarterKit`, never disabled here) already handles this correctly — it's a real ProseMirror `Decoration.widget` at the exact position, and typing into it works out of the box (inserts a paragraph there automatically). The only actual problem was cosmetic: its default widget is a black horizontal bar (`.ProseMirror-gapcursor:after { border-top: 1px solid black }`, injected into `<head>` by the Tiptap bundle at runtime), which looks broken next to the app's blue vertical `caret-color: #007aff`. Fixed with a pure CSS override in `editor.html` (near the `.ProseMirror { caret-color }` rule) that redraws the widget as a vertical `border-left` bar in the same blue — scoped under `.ProseMirror .ProseMirror-gapcursor:after` so its higher specificity reliably beats the later-injected default regardless of DOM order. An earlier attempt patched this by forcing a trailing paragraph into the document (`appendTransaction`) and then stripping it back out in `toWordPressHTML` before save — don't do that: it only covered the doc-end case, left the same bug everywhere else an atom neighbors a gap, and permanently added a "insert fake HTML, then remember to remove it" liability to the save path for a rendering-only problem.
- **`marked` is a second, separate IIFE bundle** — `marked-bundle.js` (`window.MarkedBundle`, ~40 KB) is generated by `./Scripts/bundle-marked.sh` and loaded by its own `<script src>` in `editor.html` between the Tiptap bundle and `editor-transforms.js`. Only `window.insertMarkdown` consumes it. Kept out of `bundle-tiptap.sh` on purpose so regenerating a Markdown parser can't drift the editor onto a newer Tiptap 2.x.
- **Tiptap is bundled locally as IIFE** — `Sources/QuillKit/Resources/tiptap-bundle.js` is a minified IIFE bundle (`window.TiptapBundle`) generated by `./Scripts/bundle-tiptap.sh` (requires `node`). No CDN requests at runtime; editor loads instantly from disk. IIFE format is required — `type="module"` + ES module `import` statements do NOT work with `file://` URLs in WKWebView (silent failure, `editorReady` never fires). `editor.html` loads the bundle via `<script src="./tiptap-bundle.js">` and destructures from `TiptapBundle`. To update Tiptap 2.x: re-run the script and rebuild. To upgrade to Tiptap 3.x: bump `"^2"` → `"^3"` in the script's package.json block, verify exports in `entry.js` still exist, and check for API changes in `editor.html`.
- **Known unfixed edge case: `galleryBlock.sizeSlug` is per-gallery, not per-image** — `GallerySheet`'s Size picker applies one slug to every image in the gallery, and `parseHTML`'s `getAttrs` derives `node.attrs.sizeSlug` from only `imageFigures[0]`'s class, discarding size info for images 2..n in a *loaded* gallery with heterogeneous per-image sizes (real WordPress galleries can have these). This is currently harmless — a loaded gallery's `sourceHTML` renders verbatim, so `attrs.sizeSlug` is never read back for that case — but it's lossy ground truth that the next feature to trust it (e.g. an edit-existing-gallery flow, implied by v1's insert-only scoping) would need to fix first, by moving size onto each `images[]` entry instead of the node. Deliberately left unfixed as of 2026-07-09 since v1 has no gallery-editing UI to expose the gap.
- **Known unfixed edge case: image link toggle collapses all WordPress link destinations to "media"** — `ResizableImage.linkTo`/`linkHref` only models "linked to full image" vs. "not linked"; any `<a>` wrapping the image (attachment-page link, custom URL, or a true full-image link) is detected as `linkTo: 'media'` on load, since detection just checks for a non-empty `href`. A passive load→save round-trip is lossless (the original `href` is preserved verbatim), but toggling the link off then back on replaces the original destination with the image's own full-resolution URL, since there's no attribute tracking the original destination *type*. Deliberately left unfixed as of 2026-07-10 — a real fix means modeling WordPress's actual `linkDestination` enum (`attachment`/`custom`/`media`/`none`), a larger schema change than the surrounding bug-fix pass warranted.
- **Known unfixed edge case: `AIResultPanel`/`beginAIOperation` reentrancy** — `beginAIOperation()` in `editor.html` unconditionally overwrites the module-level `_aiFrom`/`_aiTo`/`_aiOriginalHTML` globals with no guard against a prior operation still being in flight (`_aiInProgress` isn't checked). If the user selects different text and triggers a second right-click AI operation before the first one's Claude response returns and its `AIResultPanel` appears, the second call's globals clobber the first's, and `AIResultPanel.show()`'s existing monitor-dedup fix (below) only prevents the resulting double keypress-handler firing — it does not stop the first operation's `onAccept`/`onDiscard` callbacks from being silently overwritten and orphaned. Never confirmed in practice; a real fix needs `beginAIOperation()` to reject (or queue) a second call while `_aiInProgress` is true. Deliberately left unfixed as of 2026-07-05 pending a discussion of the UX tradeoff (reject vs. queue vs. auto-discard the first).
- **Cmd+click to open links** — `handleClick` in `editorProps` checks `event.metaKey`, walks up the DOM to find an `<a>` element, and posts its `href` to the `openLink` Swift message handler. Fragment-only hrefs (`#...`) are skipped via `el.getAttribute('href').startsWith('#')` — without this, footnote marker `<a href="#UUID">` elements resolve to `file:///...#UUID` (truthy), which `isAllowedExternalURL` blocks, but `handleClick` returns `true` and swallows the click. The `body.cmd-held` CSS class (toggled by keydown/keyup/blur) adds `cursor: pointer` and `text-decoration: underline` to links while Cmd is held.
- **`ResizableImage` Tiptap extension** — `Image` from `@tiptap/extension-image@2` must be imported as a named import (`{ Image as TiptapImage }`) so the default export doesn't shadow the name. `ResizableImage` extends `TiptapImage` and adds `width`, `height`, `mediaId` attributes. It parses standard `<img width="..." height="...">` and `class="wp-image-{id}"` on load; serializes to `width="..."`, `height="..."`, `data-media-id="..."` on output.
- **`ImageNodeView` is a plain JS class, not a React/Svelte component** — registered via `addNodeView()` returning `new ImageNodeView(node, editor, getPos)`. Implements the ProseMirror NodeView interface: `dom`, `update()`, `selectNode()`, `deselectNode()`, `destroy()`, `stopEvent()`, `ignoreMutation()`. `stopEvent` returns `true` for `mousedown` on `.resize-handle` elements so ProseMirror doesn't steal the event.
- **`.image-frame` div wraps `<img>` and resize handles** — `ImageNodeView` creates an inner `.image-frame` div (child of `.image-wrapper`, sibling of `<figcaption>`) that wraps only the `<img>` and the four `.resize-handle` elements. All handle CSS positions are relative to `.image-frame`, so handles align to the image dimensions, not the full wrapper including caption height. `.image-frame { position: relative; display: inline-block; line-height: 0; }`. Do not put handles directly inside `.image-wrapper`.
- **Non-leaf NodeView + NodeSelection: must intercept `stopEvent`** — because `ResizableImage` has `content: 'inline*'` with `contentDOM = figcaption`, ProseMirror maps any click inside the `dom` wrapper to a text cursor inside `contentDOM` rather than creating a NodeSelection. This means `selectNode()` is never called, so the blue outline, resize handles, and image toolbar never appear. Fix: in `stopEvent()`, intercept `mousedown` where `!this.figcaption.contains(e.target)`, call `e.preventDefault()`, dispatch `this.editor.commands.setNodeSelection(pos)`, and return `true`. Without this, clicking an image does nothing visible.
- **`ResizableImage` has `content: 'inline*'` for captions** — the image node is no longer atomic (leaf). `ImageNodeView` exposes `contentDOM = this.figcaption` so ProseMirror manages caption text directly inside the `<figcaption>`. `ignoreMutation` returns `false` for mutations inside `contentDOM` (so ProseMirror tracks caption edits) and `true` for all other mutations (resize handles, wrapper). `renderHTML` outputs `['figure', {}, ['img', HTMLAttributes], ['figcaption', 0]]` — the `0` is the ProseMirror content hole. `parseHTML` has `contentElement: 'figcaption'` on the `figure.wp-block-image` rule so existing WordPress captions load correctly.
- **Tiptap node attrs: a per-attribute `parseHTML` stub must return `null`/`undefined` to be a true no-op, not a literal default value** — Tiptap's schema builder runs every attribute's own `parseHTML(el)` extractor *after* a parse rule's `getAttrs(el)` and merges the result on top, overriding any key it returns a non-null/non-undefined value for. `figureClass`/`figureId` on `ResizableImage` stub `parseHTML: () => null` (filtered out of the merge, so `getAttrs`'s computed value survives); `linkTo` was initially stubbed `parseHTML: () => 'none'` (matching its schema default, to keep the bare `img[src]` fallback rule sane) — but since `'none'` is non-null, it silently overwrote the *correct* `'media'`/`'none'` computed by the `figure.wp-block-image` rule's own `getAttrs` on every single parse. Fix: stub dead attrs with `parseHTML: () => null` always, regardless of the attribute's own default — let the ProseMirror schema `default` fill in genuinely-unset values instead.
- **`ResizableImage`'s per-attribute `parseHTML` can double as a fallback for parse rules with no `getAttrs` of their own** — `linkTo`/`linkHref` no longer use the dead-stub pattern above; their own `parseHTML(el)` actively detects an `<a>` wrapper (checking `el.tagName === 'FIGURE'` first to locate the real `<img>`, since `el` is whatever element the *matching rule* matched). This makes them work for both the `figure.wp-block-image` rule (which also computes the same value via its own `getAttrs`, redundant but consistent) **and** the bare `img[src]` fallback rule (used for classic/pre-Gutenberg linked images with no figure wrapper), which has no `getAttrs` at all. Before this, classic linked images silently lost their link on the first save in Quill. If you add a new attribute that must work under a rule without `getAttrs`, give it real per-attribute `parseHTML` logic rather than a `() => null` stub.
- **`<a>` wrapper detection for image links must check for a non-empty `href`, not just `tagName === 'A'`** — an `<a>` with no `href` or `href=""` (malformed/hand-edited HTML) is not a real link; treating it as one sets `linkTo: 'media'` (toolbar shows the toggle as "on") while `renderHTML`'s truthy check on `linkHref` omits the `<a>` on save anyway — a UI/saved-state mismatch. Both `ResizableImage`'s figure-rule `getAttrs` and its attribute-level `parseHTML` fallback require `linkEl.getAttribute('href')` to be truthy.
- **Use `state.tr.setNodeMarkup(pos, null, attrs)` to commit image attribute changes** — do NOT use `editor.chain().updateAttributes()` for the image node; it resets ProseMirror's selection state. `setNodeMarkup` commits only the attributes without touching selection. Always get `pos` from `getPos()` and check `typeof pos === 'number'` before dispatching.
- **`#image-toolbar` is `position: fixed`, not an absolute child of the NodeView** — the toolbar div lives at the body level (inside `#editor-wrap`'s sibling scope) to avoid overflow clipping. Positioned via `getBoundingClientRect()` of the image wrapper. A scroll listener (`tb._scrollHandler`) is attached to `#editor-wrap` when shown and removed when hidden — always clean it up in `_hideImageToolbar()`.
- **`tb._activeNodeView` stored on the toolbar DOM element** — the currently selected `ImageNodeView` instance is stored directly as a property on the `#image-toolbar` element (`tb._activeNodeView`). Toolbar event handlers read this to find the active node. Always null-check it; it is set to `null` by `_hideImageToolbar()`.
- **80 ms delay in `deselectNode()`** — without the `setTimeout(..., 80)`, clicking a toolbar input deselects the image before the input receives focus, which would immediately trigger `_hideImageToolbar()` and close the toolbar. The delay lets the input's `focus` event fire first; the timeout body then re-checks `tb.contains(document.activeElement)` before hiding.
- **Image Reset button reads `_sizeData` from the Full size button** — when the user clicks Reset in the image toolbar, the handler checks `document.querySelector('#image-toolbar [data-size="full"]')?._sizeData`. If present, it restores `src`, `width`, and `height` from that object (the original full-resolution image). If absent (media sizes not loaded), it clears only the explicit constraints (`width: null, height: null`). `_applyAttrs` also defensively clears `img.style.width/height` to prevent lingering inline styles from interrupted drag operations.
- **Per-image toolbar controls gated on `requestMediaSizes` data must degrade, not disappear, for images with no `mediaId`** — the "Link to Full Image" toggle (`#img-tb-link`) was originally hidden entirely (`display: none`) whenever `fullBtn?._sizeData` wasn't loaded, which is permanent for any externally-sourced image (drag-dropped/pasted, no `mediaId` — `requestMediaSizes` is only posted when `mediaId != null`). If such an image was already linked (parsed `linkTo: 'media'` on load), the toggle was invisible and unreachable, with no UI path to see or undo the link. Fixed: `_updateNamedSizeButtons` always shows `#img-tb-link` (unlike the Thumb/Medium/Large/Full preset buttons, which correctly stay hidden without size data — there's no better URL to jump to for those). The click handler falls back to `nv.node.attrs.src` for `linkHref` when `fullBtn._sizeData` isn't available, so toggling still works, just without a WordPress-resolved "full" URL. Follow this "always show, degrade the action" pattern for any future per-image toolbar control gated on async media data.
- **AI buttons are in the Tiptap toolbar, not the SwiftUI toolbar** — `btn-generate` (pencil SVG) and `btn-evaluate` (checkmark-circle SVG) live in `#ai-toolbar-group` in `editor.html`. `window.setAIEnabled(bool)` shows/hides the group; `window.setEvaluating(bool)` disables/enables the evaluate button during a run; `window.setEvaluationPanelOpen(bool)` toggles the `.active` class on the evaluate button. These fire from `EditorCoordinator` via `onTriggerGenerate`/`onTriggerEvaluate` message handlers. Do NOT re-add AI buttons to the SwiftUI toolbar — they were moved to Tiptap so the pencil and checkmark icons are inside the editor scroll region alongside other toolbar controls.
- **`showAIResult` inserts at block-node boundaries, not text positions** — using `setTextSelection({ from, to }).insertContent(html)` with character positions inside a paragraph causes ProseMirror to split the paragraph at those points, leaving empty `<p>` fragments before and after the inserted content. Instead, expand to node boundaries: `$from.before($from.depth)` / `$to.after($to.depth)`, then call `insertContentAt({ from: nodeFrom, to: nodeTo }, html, { parseOptions: { preserveWhitespace: false } })`. The `preserveWhitespace: false` option is required — the default `'full'` causes ProseMirror to wrap the `\n` characters Claude emits between `<p>` tags into blank paragraph nodes. For container operations (lists/tables), `showAIResult(html, cFrom, cTo)` re-derives container boundaries from `_aiFrom` after restoring the original document — saved positions shift during the `getHTML`/`setContent` round-trip for tables. Both `_aiFrom` and `_aiTo` are clamped to `docSize` before calling `doc.resolve()` to prevent `RangeError` on position shift.
- **AI operations detect list/table context** — `beginAIOperation()` walks `$from.depth` to detect parent `bulletList`, `orderedList`, or `table` nodes. When found, it sends the full container text to Claude with context-specific prompts (via `AIPromptBuilder.operationPrompt(context:)`) and returns `containerFrom`/`containerTo` so `showAIResult` can replace the whole container. The context menu's ancestor walk in `DroppableWebView.rightMouseDown` requires `sel.from !== sel.to` to prevent a collapsed cursor (click with no selection) from triggering AI operations on an entire table/list.
- **Strip inter-block whitespace text nodes before inserting AI HTML** — even with `preserveWhitespace: false`, ProseMirror can create a blank paragraph from the first whitespace text node at the start of a slice. Before calling `insertContentAt`, parse the HTML through a temporary `div`, remove whitespace-only `childNodes` (text nodes between block elements), and use the resulting `innerHTML`. This ensures zero inter-paragraph whitespace reaches ProseMirror's parser.
- **Embeds render as static cards via `EmbedNodeView`** — `renderHTML` returns a DOM node (not an array spec) because the wrapper needs raw newline text around the URL and the caption is raw preserved HTML. Caption editing is unsupported; `caption` attr round-trips verbatim.
- **`FootnotesList`/`FootnoteItem`/`FootnoteMarker` use `priority: 110`** — so their parse rules beat the generic `ol`/`li` rules. Do not remove the priority.
- **Footnote numbers in the editor come from CSS counters** (`sup.fn a::before`); the saved number is written by `toWordPressHTML`. Anchors in the editor DOM are intentionally empty.
- **`FootnoteSync` `appendTransaction` rebuilds the list children** — deleting a marker deletes its entry (including typed text) by design.
- **Footnote back-arrow (`↩`) in editor vs. saved HTML** — `FootnoteItemNodeView` renders a `<a class="fn-backref">↩</a>` button at the end of each list item DOM node; clicking it dispatches `setTextSelection` to jump to the matching marker. This button is a NodeView artifact and does NOT appear in the ProseMirror doc or saved HTML. The saved backref (`<a href="#ref-fn-…" class="footnote-backref">↩</a>`) is added by `toWordPressHTML`, which also sets `id="ref-fn-{UUID}"` on each marker `<sup>`. The `.footnote-backref` class is stripped on load in `FootnoteItem.parseHTML()`'s `getAttrs` (`editor.html:1420`); the idempotency guard at `editor-transforms.js:134` prevents double-wrapping on save. The back-arrow element has `contentEditable='false'` and `tabIndex=-1` so it is not editable or tab-focusable; it is positioned with `position: absolute` + `transform` inside its `position: relative` `<li>` parent, keeping it outside the text flow.
- **`_ancestorDepth($pos, typeName)` helper** — returns the ProseMirror depth of the nearest ancestor with the given node type name, or -1 if not found. Used by imageCaptionExit, blockquote Enter, blockquote toggle, cite toggle, and cite Enter handlers. Walks `$pos.depth` down to 0.
- **Blockquote Enter handler depth guard** — `CustomBlockquote`'s Enter keyboard shortcut returns `false` when `$from.depth > bqDepth + 2`, so nested structures inside blockquotes (tables, lists) are handled by their own extensions. Without this guard, `tr.split(pos, depth)` with depth > 1 would corrupt nested node structures.
- **Blockquote toggle-off strips cite before lifting** — the blockquote toolbar command deletes the cite node (if present) before calling `toggleBlockquote()`. Without this, ProseMirror's `lift` fails silently because cite has no `group` and cannot exist at doc level. The cite text is lost (undoable) — this is intentional since cite only makes sense inside a blockquote.
- **Cite toggle button (`#btn-toggle-cite`)** — appears in the toolbar when the cursor is inside a blockquote. Adds or removes a cite node at the end of the blockquote. The button's active state is updated by `updateToolbar()` via `editor.isActive('cite')`.
- **Image caption Enter (`imageCaptionExit` plugin)** — ProseMirror `handleKeyDown` plugin on `ResizableImage` that intercepts Enter inside image captions and creates a new paragraph after the image node. Uses `handleKeyDown` (not `addKeyboardShortcuts`) so it fires before all keymap plugins.
- **`_fnPassthrough` allows Backspace/Delete through footnote keyboard guards** — the `_fnPassthrough` Set contains `'Backspace'` and `'Delete'`. The keyboard shortcut wrappers on BulletList, OrderedList, Blockquote, and CodeBlock return `!_fnPassthrough.has(k)` when in a footnote — `false` for Backspace/Delete (allowing default behavior) and `true` for all other keys (blocking them). Args are forwarded via `(...args) => ... fn(...args)`.
- **Find & replace decorations use `PluginKey('findReplace')`** — separate from spell check; `_refreshFind` dispatches meta-only transactions which do not re-fire `update`.
- **Stats freeze in code view** and refresh on `_exitCodeView()`/`setContent` via `_postStats()`.
- **`crypto.randomUUID()` is available in WKWebView on macOS 13+ even with `file://` URLs** — WebKit treats `file://` as a secure context for the Web Crypto API. Do not polyfill `randomUUID` — it is natively available and used by `insertFootnote()`.
- **`updateToolbar()` caches DOM button references** — `_toggleBtns`, `_blockBtns`, `_undoBtn`, `_redoBtn`, `_tableControls`, `_bqControls`, `_btnToggleCite`, `_embedBtn`, `_footnoteBtn` are resolved once at init and reused on every `onTransaction` call. Do not use `document.querySelector` for toolbar buttons inside `updateToolbar()` — it runs on every keystroke.
