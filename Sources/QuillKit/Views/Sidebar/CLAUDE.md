# Sidebar views (SidebarView, PostListRow)

Implementation gotchas specific to this directory. See the root `CLAUDE.md` for architecture, build/test commands, and cross-cutting conventions.

## Known gotchas

- **Sidebar post list is a real `List(selection:)` with `.listStyle(.sidebar)`** — converted on the `native-ui` branch (2026-09-19). It was `ScrollView { LazyVStack { ForEach { Button } } }`, which existed only to repaint `NSTableRowView`'s blue selection; the native selection is now the wanted appearance, so that reason is gone. Rows carry `.tag(item.id)` and the list binds to `itemSelection`, an id binding: a save replaces the cached post but not `selectedItem`, and a whole-value tag then matched no row, so the highlight vanished and Trash left the editor open (fixed 2026-10-08). Compare selection by id everywhere in this view. Do not make `PostItem` compare by id instead: SwiftUI uses `==` to decide whether `PostListRow` needs redrawing, so a saved title would stop updating in the sidebar. The empty/loading states ride in `.overlay`, because a `List` cannot show them as rows. Do NOT revert to `ScrollView+LazyVStack`.
- **The search field is an AppKit wrapper so the picker can sit above it, and that is the only reason** — `SidebarSearchField` replaced two `.searchable` calls on the `native-ui` branch (2026-09-19). `.searchable(placement: .sidebar)` is always hoisted to the top of the sidebar column, so nothing can be placed above it; that alone rules out picker-above-search. One `SidebarSearchField` now serves every section, switching binding (`searchText` / `mediaSearchText`) and prompt off `selectedSection`, which is why `MediaSidebarSection` no longer carries its own `.searchable`. The prompt is `"Search \(selectedSection.shortTitle)"` — Search Posts, Search Pages, Search Drafts, Search Media (2026-09-20). **`.searchable(placement: .toolbar)` does work** and was built and run on 2026-09-20 to check: it filters correctly, switches prompt per section, fits the 900pt minimum width with a post open, and — unlike the AppKit field — does *not* take first responder at launch, so it needs no focus guard at all. It was rejected on layout, not on feasibility: the toolbar puts the field to the right of the editor's own buttons, far from the sidebar list it filters. Keeping the AppKit field is a deliberate trade of ~79 lines for that adjacency. If the sidebar layout is ever reworked for another reason, take `.searchable` then and delete this component, `releaseSearchFocus()` and the next entry with it.
- **`SidebarSectionPicker` is custom SwiftUI, and `.glassEffect()` is what makes that non-negotiable** — it was an `NSSegmentedControl` wrapper until 2026-09-20. Three measured findings drove the swap, all verified on screen in the running app. `NSSegmentedControl` renders `setImage` and `setLabel` together, but four icon+label segments need ~266pt against the 240pt the sidebar gives, and `segmentDistribution = .fillEqually` cannot shrink a segment below its fit size, so it overflows and clips the end segments; a 10pt `SymbolConfiguration` recovers only 13pt of the 27pt gap. `selectedSegmentBezelColor` is silently ignored in this appearance, so the accent cannot tint the selection. And the control's 24pt height is the *bezel's* fixed height, which no `controlSize` or SwiftUI frame moves — that is what rules out stacking an icon over a label. The macOS 27 `role = .tabs` only removes the separator pips; it solves none of the three. Going custom no longer costs the system material, because `.glassEffect(_:in:)` (macOS 26+, `Glass.regular/.clear/.identity` with `.tint(_:)` and `.interactive(_:)`, plus `GlassEffectContainer`) has Apple draw the Liquid Glass while the layout stays ours. Unselected segments pass `.identity` rather than dropping the modifier, so all four keep one view identity. A custom row *does* honour `.frame(maxWidth: .infinity)` — the width matches the search field exactly at 10–250 — so only the `.segmented` `Picker` ever had the centring problem. Accessibility is now hand-written (`.accessibilityLabel`, `.isSelected`) and must stay: `NSSegmentedControl` gave it free. An amber `.tint(.accentColor)` was built and rejected — it saturates hard enough to read as a painted chip instead of glass.
- **The picker no longer claims first responder the way `NSSegmentedControl` did — re-verify the search-focus guard after touching it** — the `ClickToFocusSearchField` entry below depends on nothing else in the sidebar taking first responder back. That reasoning was written against `NSSegmentedControl`, which never claims it by design; the picker is now SwiftUI buttons. Scripted clicks cannot test this (see the scripted-clicks gotcha in `docs/gotchas.md`), so it needs real clicks.
- **`ClickToFocusSearchField` refuses first responder only while AppKit is assigning it, and that guard is load-bearing** — AppKit hands first responder to the only focusable control in a SwiftUI window, so a plain `NSSearchField` grabs focus on launch and then never gives it up: SwiftUI `List` rows do not claim first responder when clicked, so nothing takes it back. The subclass sets `refusesFirstResponder = true` in `viewDidMoveToWindow` and clears it one runloop turn after the window becomes key, which lands *after* the automatic assignment. Until 2026-09-20 it overrode `acceptsFirstResponder` to return false until its own `mouseDown` fired; that also blocked Tab, Full Keyboard Access and VoiceOver forever, which is why it changed. Do NOT "fix" launch focus with `window.makeFirstResponder(nil)` from `viewDidMoveToWindow` instead — that was tried and it silently blocks click-to-focus afterwards. `SidebarView.releaseSearchFocus()` handles the other half, clearing focus on `selectedItem` / `selectedSection` change. This is the one component in the app where a change can break silently with every test still green: verify any change here with real `CGEvent` clicks — see the scripted-clicks gotcha in `docs/gotchas.md`, and the three focus checks in `docs/testing-plan.md` §7.2.
- **The sidebar toggle is Quill's own `SidebarToggleButton`, and Refresh/+ appear only once the column is fully on screen** — `.toolbar(removing: .sidebarToggle)` (on `SidebarView`; it has no effect on `ContentView`) drops the system toggle because macOS pins it to the sidebar's trailing edge, which makes the NetNewsWire order (toggle, Refresh, +) impossible. Keep exactly one toggle in the toolbar: a second toggle swapped in for the collapsed state flashes on every click. Refresh and + are gated on `isFullyOnScreen` (from `onGeometryChange`), not just `columnVisibility`, because items added while the column is still sliding in overflow into a transient `»` menu; left in place while collapsed, they sit in that `»` menu permanently.
- **`.navigationSplitViewColumnWidth` goes on `SidebarView` in `ContentView`, not inside `SidebarView`'s body** — applied to the body's root `VStack`, SwiftUI ignored it at launch: a fresh launch opened the sidebar at 144pt instead of 310pt, and a saved width of 140pt was restored as-is, below the 260pt minimum. Divider drags still honoured the minimum, so the bug only showed at launch. Moved on 2026-09-25 and verified by measuring the column through Accessibility after deleting the saved `NSSplitView Subview Frames … SidebarNavigationSplitView` key in `com.quill.app` defaults (now `com.siolon.quill`): 310pt fresh, and 260pt when a 140pt width is saved. Which modifier in `SidebarView`'s chain blocks it was not isolated. That defaults key embeds a framework address that changes between boots and rebuilds, so SwiftUI loses the saved width and stale copies pile up (harmless). `ContentView` therefore saves the width itself under the `sidebarWidth` defaults key (from `onGeometryChange`, skipped while collapsed) and passes it as `ideal` on the next launch; the default is 260pt. Verified 2026-10-05 by deleting the split-view keys: a dragged 295pt came back at 295pt, and with no `sidebarWidth` key the sidebar opens at 260pt. A window too narrow for the detail column squeezes the sidebar to 260pt at launch, and that squeezed width is what gets saved — test restore in a wide window (1300pt).
- **Taxonomy cache `clearAll()` is gated on site URL change** — `SidebarView.loadAllSections()` compares a stored `UserDefaults` site URL before calling `clearAll()`. Normal launches serve from the 24-hour SQLite cache; only a site URL change triggers a fresh fetch. Do NOT call `clearAll()` unconditionally — it defeats the cache on every launch.
- **`SplitItemCollapseFix(behavior: .sidebar)` sets the sidebar item's `collapseBehavior` to `.useConstraints`; without it a drag-collapse followed by dragging the sidebar back out grows the window** — with the default behaviour the sidebar uncollapses as `preferResizingSplitViewWithFixedSiblings` (see `NSSplitViewItem.h`): AppKit adds a transient `window hosting view width == current + sidebar @510` constraint, above `WindowSizeStayPut`, so a 900pt window became 1160pt while the detail kept its width. Traced 2026-10-05 from the `NSWindow.didResizeNotification` stack (`_uncollapseArrangedView:` → `NSSplitViewController _collapse:…` → `_changeWindowFrameFromConstraintsIfNecessary`). `.preferResizingSiblingsWithFixedSplitView` did not help (the window still grew), and neither did `canCollapseFromWindowResize = false`; `canCollapse = false` worked but SwiftUI resets it on every toggle. SwiftUI leaves `collapseBehavior` alone across toggles, so setting it once in `viewDidMoveToWindow` is enough. The toolbar toggle never had the bug. After a drag-uncollapse the sidebar reappears at its 260pt minimum and follows the pointer from there.
- **`.task(id:)` reruns on every view remount, not just id changes** — `AppState.lastLoadedCredentials` and `hasCheckedForUpdate` guard `loadAllSections()` and `UpdateChecker.check()` from re-running on a remount. Both are set only on a *successful* completion (not on failure): `lastLoadedCredentials` after a successful `loadAllSections()`, and `hasCheckedForUpdate` only inside the `do` branch after `UpdateChecker.check()` returns without throwing — `UpdateChecker.check() throws` specifically so a transport/decode failure (vs. "checked fine, no update found") can be told apart and left to retry on the next remount instead of being silently skipped for the rest of the session. The original trigger was `ContentView` including the sidebar conditionally (`if appState.isSidebarVisible`), so every hide/show remounted it; `isSidebarVisible` was deleted on the native-ui branch and `NavigationSplitView` now owns column visibility, so that particular remount is gone. Keep the guards: they are cheap, and nothing documents that SwiftUI will never remount this view for another reason. Because `lastLoadedCredentials` stays unset after a failed launch load, Retry, ⌘R (`triggerRefresh`) and the toolbar Refresh all call `refresh()`, which re-runs `loadAllSections()` in that state (bumping `mediaRefreshToken` too when Media is showing, since `loadAllSections()` never reloads media) and `loadCurrentSection()` otherwise. Calling `loadCurrentSection()` straight away reloads one section and clears the shared `listError`, so the other section then reads "No pages yet" with nothing loaded.
- **Delete state in SidebarView** — `itemPendingDelete: PostItem?` drives the confirmation alert; `deleteError: String?` drives the error alert. Both are `@State` locals in `SidebarView`. Setting `itemPendingDelete` non-nil triggers the alert; the confirm button clears it and calls `performDelete` in a `Task`.
- **Section switches go through `AppState.switchSection`, never a direct `selectedSection` write, or the picker's selected button slides up** — switching sections while an inspector is open (Media Info or Post Settings) tears down the inspector's split item in the same layout pass, and AppKit lays the sidebar out at its 147pt fitting height for that one pass, pinned to the window bottom with its split item at x = -260. The selected segment's Liquid Glass animates back from there. `switchSection` closes both inspectors without animation, then sets the section 10ms later, so the two changes land in different passes. The delay is a timer on purpose: a plain `DispatchQueue.main.async` drains before the commit and folds both changes into one pass. 1ms worked from a button but leaves no margin after a menu closes. Traced 2026-10-08 with frame logging on every AppKit ancestor of the sidebar. Ruled out: `SplitItemCollapseFix(.inspector)` on the media inspector, closing the inspector in the same update as the switch, and removing the sidebar's own `SplitItemCollapseFix`. Side effect: the media inspector no longer reopens when you return to Media. `PostEditorView.swift`'s local-draft publish still writes `selectedSection` directly. It swaps `selectedItem` without clearing it, so the editor and its inspector are not torn down and it does not slide (verified 2026-10-08 by publishing a local draft as a WordPress draft with Post Settings open). Workaround entry: `docs/platform-workarounds.md`.
- **Media sidebar when Media tab active** — `SidebarView` swaps the post list for `MediaSidebarSection()` when `selectedSection == .media`. Do not remove that `else` branch or replace it with `Spacer()`. Since 2026-09-19 the section picker and search field sit *above* that branch in the `VStack`, so both stay visible in Media mode — the picker must, because it is the only way back out, and the search field retargets to `mediaSearchText` with a "Search Media" prompt. Earlier wording said search was hidden here; that stopped being true when the two `.searchable` calls became one shared field.
- **`UpdateChecker` runs once on launch via `.task` in `SidebarView`** — reads the latest release from the GitHub API, strips the tag's `v` prefix, compares with `CFBundleShortVersionString`, and sets `appState.updateAvailable` if newer. `dismiss()` saves the version to `UserDefaults` so it won't reappear. The ephemeral `URLSession` is invalidated after use via `defer { session.invalidateAndCancel() }`.
- **`updateRow` must stay the FIRST row in the `postList` List** — it sat after the `ForEach` until 2026-09-20, which put it below every post. The banner rendered correctly and was visible for the second before the list loaded, then vanished off the bottom of a hundred-row list. Nothing fails and no test catches it.
