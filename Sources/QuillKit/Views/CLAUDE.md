# Top-level views (ContentView)

Implementation gotchas specific to this directory, split out from the project root `CLAUDE.md` (2026-07-11) to keep the root file lazy-loaded. See the root `CLAUDE.md` for architecture, build/test commands, and cross-cutting conventions.

## Known gotchas

- **SwiftUI silently reverts `titlebarAppearsTransparent` — the title bar fix must re-assert it** — the warm title bar in `ContentView.swift` needs three things at once: `.fullSizeContentView` kept *out* of the style mask (with it, content sits under the bar and shows through as separate sidebar/editor color zones; macOS re-adds the flag on every full-screen transition), `titlebarAppearsTransparent = true` (this hides `NSTitlebarBackgroundView` so the 32pt strip renders `window.backgroundColor` directly), and `window.backgroundColor = .wpTitleBarBg`. The trap: SwiftUI's own `AppKitWindow` sets `titlebarAppearsTransparent` back to `false` ~0.1s after `viewDidMoveToWindow` runs, during its window setup. Applying the fix once therefore looks like it does nothing at all — the bar renders the stock white system material and no amount of color-token tweaking changes it. `WindowObservingView` observes `didUpdate` (plus `didExitFullScreen`) and re-applies whenever the flag is found `false`, which is what makes it stick. **A light/dark appearance switch resets the flag the same way**, and the notification observers only catch that once the window next updates — so the bar sits white until the user happens to click it. `WindowTitleBarFix` therefore reads `@Environment(\.colorScheme)` and re-applies from `updateNSView`, which SwiftUI re-runs on every appearance change. Both hooks are needed: the notifications cover full-screen and stray resets, the environment read covers appearance flips. Both were verified 2026-07-24 by instrumenting the live window and by toggling the system appearance via `osascript`, checking the bar each time without touching the window. If this ever regresses, the quickest confirmation that the mechanism still works is to set `window.backgroundColor` to red and watch the bar turn red.
- **Don't derive the title-bar color from a screenshot — measure or judge it on the real display** — during the same session, downsampled screenshot captures made `#F2F1EF` look white and led to a wrong "the strip composites lighter" conclusion and a much-too-dark `#E4E1DC`. The correct value turned out to be plain `wpSidebarBg`. The panels carry the `WarmPanelBackground` diagonal shimmer while the flat bar cannot, so small mismatches are expected across the window width; judge the seam on the actual screen.
- **Layout uses `HStack + SoftPanelBoundary`, not `NavigationSplitView` or `HSplitView`** — `ContentView` uses a plain `HStack(spacing: 0)` with `SoftPanelBoundary()` between the sidebar/editor and editor/settings-panel boundaries (replaces `Divider()`). `NavigationSplitView` reinstates macOS Tahoe sidebar chrome (drop shadows, raised layer). `HSplitView` renders a draggable resize cursor on panel dividers even when frames are fixed. Do NOT switch to either.
