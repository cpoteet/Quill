# Top-level views (ContentView)

Implementation gotchas specific to this directory, split out from the project root `CLAUDE.md` (2026-07-11) to keep the root file lazy-loaded. See the root `CLAUDE.md` for architecture, build/test commands, and cross-cutting conventions.

## Known gotchas

- **SwiftUI silently reverts `titlebarAppearsTransparent` — the title bar fix must re-assert it** — the warm title bar in `ContentView.swift` needs three things at once: `.fullSizeContentView` kept *out* of the style mask (with it, content sits under the bar and shows through as separate sidebar/editor color zones; macOS re-adds the flag on every full-screen transition), `titlebarAppearsTransparent = true` (this hides `NSTitlebarBackgroundView` so the 32pt strip renders `window.backgroundColor` directly), and `window.backgroundColor = .wpTitleBarBg`. The trap: SwiftUI's own `AppKitWindow` sets `titlebarAppearsTransparent` back to `false` ~0.1s after `viewDidMoveToWindow` runs, during its window setup. Applying the fix once therefore looks like it does nothing at all — the bar renders the stock white system material and no amount of color-token tweaking changes it. `WindowObservingView` observes `didUpdate` (plus `didExitFullScreen`) and re-applies whenever the flag is found `false`, which is what makes it stick. **A light/dark appearance switch resets the flag the same way**, and the notification observers only catch that once the window next updates — so the bar sits white until the user happens to click it. `WindowTitleBarFix` therefore reads `@Environment(\.colorScheme)` and re-applies from `updateNSView`, which SwiftUI re-runs on every appearance change. Both hooks are needed: the notifications cover full-screen and stray resets, the environment read covers appearance flips. Both were verified 2026-07-24 by instrumenting the live window and by toggling the system appearance via `osascript`, checking the bar each time without touching the window. If this ever regresses, the quickest confirmation that the mechanism still works is to set `window.backgroundColor` to red and watch the bar turn red.
- **`window.backgroundColor` must be assigned a *resolved* color, never the dynamic `wpTitleBarBg` token — a catalog color keeps the window on AppKit's vibrant-backdrop path** — this was the 2026-07-25 bug: the title bar was correct whenever the app *launched* in light mode (and stayed correct through any number of light/dark toggles), but launching in dark mode gave a too-dark bar that stayed wrong in light mode too. Cause: with a catalog (dynamic) `backgroundColor`, `NSThemeFrame` carries a behind-window `NSVisualEffectView` sized to the **whole** frame including the 32pt title-bar strip. It paints blurred desktop *over* `backgroundColor`, so the strip never showed the token at all — it showed wallpaper (measurably purple-tinted, `#251F23`, against `#353535` panels on a purple wallpaper). Which backdrop the window gets is decided **once, at window creation**, from the appearance in effect then — hence "whatever mode it launched in decides it" and no later toggle recovering. Assigning a resolved opaque sRGB color instead removes that view entirely: the theme frame's subviews go from `["NSVisualEffectView", hostingView, titlebarContainer]` to just the latter two. The trade-off is that a resolved color no longer tracks appearance changes, so it *must* be re-applied on every switch — that is now a second reason `WindowTitleBarFix` reads `@Environment(\.colorScheme)`, and `titleBarFixNeeded(for:)` also compares the current background against the freshly-resolved one (`NSColor` equality is exact here: same-appearance resolutions are `==`, cross-appearance ones never are). Corollary: the older "set `backgroundColor` to red and the bar turns red" sanity check only proves the mechanism in light mode; in dark mode the vibrant backdrop would have eaten the red.
- **Don't judge the title-bar color from a *downsampled* screenshot; a native-resolution pixel scan is reliable and is the fastest way to confirm the seam** — downsampled captures made `#F2F1EF` look white and once led to a wrong "the strip composites lighter" conclusion and a much-too-dark `#E4E1DC`; the correct value is plain `wpSidebarBg`. But `screencapture -x -o` at native resolution plus a run-length scan down one pixel column is decisive and was how the bug above was both found and verified: a correct title bar shows as a *single* uninterrupted colour run spanning the strip and the panel below it (e.g. `y=190..1519 #353535`, 1330 rows), and any seam splits that run in two. Two caveats: values are shifted by the display-profile→sRGB conversion, so compare regions *within one capture* rather than against the token's hex (`#F2F1EF` measures as `#F5F4F2`, `#282828` as `#353535`); and make sure Quill is actually frontmost before capturing (`open -a Quill`), or you will measure another app's window.
- **Layout uses `HStack + SoftPanelBoundary`, not `NavigationSplitView` or `HSplitView`** — `ContentView` uses a plain `HStack(spacing: 0)` with `SoftPanelBoundary()` between the sidebar/editor and editor/settings-panel boundaries (replaces `Divider()`). `NavigationSplitView` reinstates macOS Tahoe sidebar chrome (drop shadows, raised layer). `HSplitView` renders a draggable resize cursor on panel dividers even when frames are fixed. Do NOT switch to either.
