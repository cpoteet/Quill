# Editor views (EditorCoordinator, PostEditorView, DroppableWebView, LinkPickerView, TitleTextField)

Implementation gotchas specific to this directory. See the root `CLAUDE.md` for architecture, build/test commands, and cross-cutting conventions.

## Known gotchas

- **WKWebView editor loading** — `editor.html` is loaded via `loadFileURL(_:allowingReadAccessTo:)` pointing to the Resources directory in the app bundle. Do NOT use `loadHTMLString` — there is no longer a CDN import that needs a non-null origin.
- **Dark mode runtime update** — `DroppableWebView` overrides `viewDidChangeEffectiveAppearance()` to call `window.setDarkMode?(isDark)` whenever the system appearance changes while the app is running. `applyColorScheme()` in `EditorCoordinator` handles the initial load (called on `editorReady`). Both are required — the coordinator sets the initial state, the override handles live toggling. Without the override, the editor stays white if the user enables dark mode while the app is open.
- **Inline taxonomy creation** — `PostSettings.newCategoryNames` / `newTagNames` hold names typed in the panel that don't exist on the server yet. On save/publish, `PostEditorView` calls `createCategory`/`createTag` for each pending name before building the payload, inserts the returned ID into `categoryIDs`/`tagIDs`, and appends the new item to `appState.categories`/`appState.tags`. Do not remove `newCategoryNames`/`newTagNames` — they are the mechanism for deferred creation. `loadItem()` resets both, so names typed but never saved do not carry into the next post. `save()` works on a copy of `settings`; it writes a created term into the view's own `settings` (and drops the pending name) only while `stillOnPost()`, and otherwise adds it to `appState` only, so the term shows in the lists but is not ticked on whatever post is now open.
- **Taxonomy cache auto-refresh on missing IDs** — `PostEditorView.loadItem()` checks whether the loaded post's tag/category IDs are all present in `appState.tags`/`appState.categories`. If any are missing (e.g. tag created after last cache refresh), it re-fetches and saves the full list. Skipped for pages (which have no tags/categories). A `Task.isCancelled` guard follows the fetch to prevent stale writes on rapid post switching.
- **`PostEditorView.contentLoadFailed`** — set when the full-post fetch in `loadItem()` fails, leaving only the empty list-cache content applied. `save()` refuses to save while this is `true` (shows an error instead) — without this guard, a transient network failure during load followed by Save could publish empty content over a real post. `save()`, `saveLocalOnly()` and `openPreview()` all check it through `writeBlockedReason(_:)`, which also covers the block-risk alarm; preview needs both because WordPress writes an author's draft preview straight into the post. Reset to `false` at the very start of `loadItem()`, before the `.remote`/`.local` branch — it used to be reset inside the `.remote` branch only, so a failed remote load left the flag set and the *next local draft* opened inherited it and could not be saved at all, with an error naming a post the user was no longer looking at. The catch block re-checks `!Task.isCancelled && loadedItem == requestedItem` **before** setting `contentLoadFailed`/`saveError` (not after) — otherwise a fetch that fails just as the user switches to a different post would stomp that other post's state instead of being discarded. `saveError` and `blockRiskAlarm` are reset in the same place and for the same reason: `PostEditorView` is reused across posts rather than rebuilt per post, so **any** `@State` holding per-post banner or guard state must be reset in `loadItem()` or it silently follows the user to every subsequent post. `blockRiskAlarm` shipped with exactly that bug. The reset sits before the content is applied, so a genuine alarm for the newly-loaded post still arrives.
- **`.task(id: item.id)` starts BEFORE `.onChange(of: item.id)` fires, so per-post resets belong in `loadItem()`** — SwiftUI begins the `.task` body synchronously in the same update pass, and the `onChange` handler (which still sees the *previous* `item`) runs afterwards. `contentLoaded = false` used to live in that `onChange`. For a remote post the network `await` inside `loadItem()` pushed `contentLoaded = true` after the handler, so it looked fine; a local draft has no suspension point before `contentLoaded = true`, so the handler stomped the flag back to `false` and the "Loading editor…" overlay never cleared — reproducible as: open one local draft (works), open a second (stuck). Fixed 2026-09-19 by resetting `contentLoaded` at the top of `loadItem()` instead. Any future per-post state reset must go in `loadItem()` for the same reason; do not add one to the `onChange`.
- **Inside async work, check for a post switch with `loadedItem`, never `item`** — `item` is a `let` on the view struct, and a running `async` method or `Task` keeps the copy of the struct it started with, so `item.id` can never change mid-call and `item.id == capturedID` is always true. The per-post `@State` (`title`, `htmlContent`, `lastSavedServerModified`, …) *is* shared and does change, so a late response written after a switch lands on the other post. `loadedItem` is `@State` and `loadItem()` assigns it before the new post's content is applied, so `loadedItem?.id == capturedID` is the live check. `save()` and `openPreview()` use it after each network wait (2026-09-29, after a Codex review caught the `item` version doing nothing). `loadedItem` alone misses a section switch: switching sidebar sections sets `appState.selectedItem = nil`, which tears down this `PostEditorView` and builds a new one, so the old view's `loadedItem` never changes. `save()` therefore captures its title, content, footnotes, settings and conflict baseline up front, finishes for the post it started on whatever the user does, and writes view state (clean state, `lastSavedServerModified`, `settings.status`, the selection) only while `stillOnPost()`, which checks `loadedItem?.id` **and** `appState.selectedItem?.id`. Before the second check, publishing a local draft and then switching section pulled the selection back to the new post. Publishing a local draft flushes the editor once the post exists and, if the user typed during the request, stashes that newer content as the created post's autosave, so the remote load restores it instead of dropping it into the deleted draft row. A failed draft delete after a successful create is reported as a warning, not a failure, so a retry cannot publish a duplicate. Off-post, `save()` shows a toast naming the post (“Title”: Published, or “Title” wasn't saved: …), sends errors and the conflict case to that toast instead of `saveError` and the alert, and settles the autosave stash with `stashAfterSave`: deleted if it matches what was saved, otherwise kept and re-based on the saved version's `modified`. Clean state is set to what was sent, not to what is on screen. `loadFromServer` checks `loadedItem` after its fetch and applies the post through `applyRemotePost`, so Revert resets settings as well as title, content and footnotes, and a failed fetch shows a toast. Known limit: after a section switch the off-post toast is drawn on the torn-down view, so it is not seen. The 30-second autosave timer has no post check; `loadItem()` cancels `autosaveTask` after flushing the outgoing post and before applying the new one, and that cancellation is what protects it. A timer that fires during the flush still writes the outgoing post, because nothing has changed yet.
- **The editor's 500ms `contentChanged` debounce is flushed before anything reads `htmlContent`** — `save()`, `saveLocalOnly()`, `openPreview()`, the post switch in `loadItem()`, `onDisappear` and quit all `await editorHandle.flushPendingContent()` first. That calls `window.flushContent()`, which returns the pending post as `{ html, footnotes }` without sending it, and `EditorCoordinator` applies it on the main queue, behind any `contentChanged` already received, so an older message cannot land after it. `save()` and `saveLocalOnly()` set `isSaving` before that `await`, or a second ⌘S starts a second save during it. `EditorCoordinator` also drops `contentChanged`/`footnotesChanged` while a `setContent` it sent is unanswered (`unansweredSetContents`): WebKit delivers script messages and `evaluateJavaScript` replies in order, so a message arriving then was posted by the document being replaced. Quit goes through `QuillAppDelegate.applicationShouldTerminate`, which awaits `AppState.persistOpenPost` (registered by the open `PostEditorView`, keyed on its `quitToken` so a torn-down view never clears a new one's hook) and replies `.terminateLater`. Before this, ⌘Q lost everything since the last autosave, and autosave waits for 30s without a change, so steady typing was never saved.
- **Auto-dismiss timers keyed on an explicit token, not the message text** — `.task(id:)` only restarts when the *id* changes, so keying a toast's dismiss timer on the message string (`.task(id: msg)`) fails to restart the timer when two consecutive toasts share identical text (e.g. two "Image inserted" toasts from a multi-file drop) — the second toast inherits whatever time was left on the first's timer and can vanish early. `PostEditorView.presentToast(_:isError:)` is the only way toasts are shown; it bumps a `toastToken: Int` on every call, and `DesignSystem.swift`'s `toast(message:isError:token:)` modifier keys `.task(id: token)` on that counter instead of the text. Do not reintroduce a direct `toastMessage = "..."` assignment — always go through `presentToast`, or the token won't advance and the same-text case regresses.
- **Context menu — WKWebView (`DroppableWebView`)** — WebKit's Cut/Copy/Paste items use private internal selectors, so filtering by `["cut:", "copy:", "paste:"]` removes them too. `rightMouseDown` intercepts the event, evaluates `window.spellContextAtPoint?(x, y)` (for spelling suggestions), then calls `buildContextMenu(spellContext:)` and pops it up directly via `NSMenu.popUpContextMenu`. This bypasses WebKit's own menu path entirely (which did not honour `allowsContextMenuPlugIns = false`, causing AutoFill/Services leakage). `buildContextMenu` constructs a fresh menu with: spelling suggestions + separator (when a spell error is under the cursor), Cut/Copy/Paste via `NSSelectorFromString("cut:")` etc., and AI writing operations (Make Longer, Make Shorter, To Table, To List) when `aiEnabled && hasTextSelection` and the click is not inside a footnote (`window.isInFootnote`). There is no Insert Footnote item; footnotes are inserted from the toolbar's `*` button (`btn-footnote`). `willOpenMenu` is kept as a fallback for accessibility-triggered menus and sets `allowsContextMenuPlugIns = false` there too. `hasTextSelection` is updated by `PostEditorView` via the `onSelectionChanged` callback whenever the editor selection changes.
- **Spelling suggestions in the context menu** — `rightMouseDown` evaluates `window.spellContextAtPoint?(x, y)` which returns `{ word, from, to }` (ProseMirror character positions) when the click lands on a spell-error decoration, or `null` otherwise. `to` is computed via `posAtDOM(el, el.childNodes.length)` — do NOT use `from + word.length` (JS string length / UTF-16 units), which silently corrupts replacements near emoji or astral characters. `SpellContext` (private struct) and `SpellReplacement: NSObject` (private class — must be `NSObject` for use as `representedObject`) carry the data. `spellingSuggestions(for:)` uses `NSSpellChecker.guesses`; top 8 results are prepended above Cut/Copy/Paste with a separator. Applying a suggestion calls `window.replaceSpellError?.(from, to, jsonEncodedSuggestion)` which dispatches `state.tr.insertText` in ProseMirror. The `applySpellingSuggestion(_:)` action is wired directly via `#selector` inside `buildContextMenu`.
- **`NSSpellChecker` checking must run on the main thread** — use `requestChecking(of:range:types:options:inSpellDocumentWithTag:completionHandler:)`, which handles threading internally and delivers results on the main thread. Do NOT call `checkSpelling(of:...)` from a background queue — it is main-thread-only and will silently misbehave or crash.
- **External link navigation is scheme-restricted** — `EditorCoordinator.isAllowedExternalURL(_:)` allows only `http`, `https`, and `mailto` through `NSWorkspace.shared.open`. All other schemes (`javascript:`, `ftp:`, etc.) are cancelled at the navigation policy, and the only `file:` URL the web view may load is `editor.html` itself (`isEditorPage`). The media library's Open in Browser uses the same check, and `previewURL(from:)` returns nil for anything but `http`/`https`. Do not remove these checks or broaden the allowed list.
- **Context menu — title field (`TitleTextField`)** — `NSTextField` uses a shared field editor (`NSTextView`); overriding `menu(for:)` on the NSTextField subclass is never called during editing. Use `NSTextView` directly via `NSViewRepresentable` (`RestrictedTextView`) — `menu(for:)` on the NSTextView subclass IS called on right-click. Build a fresh menu with only Cut/Copy/Paste items and set an `NSMenuDelegate` to catch late-appended items. Do NOT try the NSTextField field editor delegate wrapping approach — it is fragile and AutoFill leaks through regardless.
- **Link picker uses `ObservableObject`, not `@State`, for async search results** — `LinkPickerView` is hosted in an `NSHostingController`/`NSPopover`. `@State` mutations from async `Task {}` closures do NOT trigger SwiftUI re-renders in this context. `LinkPickerModel: ObservableObject` with `@Published` properties uses Combine's `objectWillChange` which reliably triggers re-renders. Do not revert `LinkPickerModel` to `@State` properties on the view.
- **`NSHostingController.sizingOptions = .preferredContentSize` required for dynamic popover resizing** — `NSHostingController` defaults to `sizingOptions = []`, which means `preferredContentSize` is set once at initial layout and never updated. When SwiftUI content grows (e.g. search results appear), the `NSPopover` stays locked at its original height and clips the new content. Set `hosting.sizingOptions = .preferredContentSize` after creating the controller so the popover resizes automatically as content changes.
- **Link picker popover anchors to text selection rect, not toolbar button** — JS sends `showLinkPicker` with `window.getSelection().getRangeAt(0).getBoundingClientRect()` (falls back to the toolbar button rect when nothing is selected). WKWebView is flipped (Y-down, same as JS), so no coordinate conversion is needed — pass the JS rect directly to `NSPopover.show(relativeTo:of:preferredEdge:)` with `preferredEdge: .maxY`.
- **`requestMediaSizes` / `setMediaSizes` round-trip** — when an image with a `mediaId` is selected, JS posts `{ mediaId }` to the `requestMediaSizes` WKWebView message handler. Swift's `EditorCoordinator` calls `onRequestMediaSizes?(mediaId)` (an async closure wired in `PostEditorView`), serializes the result's `mediaDetails.sizes` to JSON, and calls `window.setMediaSizes(id, JSON)` back into the webview. The closure tries `appState.mediaItems` cache first, then falls back to `WordPressClient.fetchMediaItem(id:)` — this is essential for size buttons (Thumb/Medium/Large/Full) to appear on images already saved in a post, not just freshly inserted ones. `onRequestMediaSizes` is typed `((Int) async -> WPMedia?)?`; `handleRequestMediaSizes` wraps the call in a `Task {}`. Do not revert to synchronous — the cache-only approach silently breaks size buttons for existing images. Do not forget to register `"requestMediaSizes"` in `EditorView.makeNSView` via `config.userContentController.add(context.coordinator, name: "requestMediaSizes")`.
- **`evaluationTask` must be cancelled on post switch and view disappear** — `executeEvaluation()` is stored as `@State private var evaluationTask: Task<Void, Never>?`. `onChange(of: item.id)` and `.onDisappear` both call `evaluationTask?.cancel()` before clearing `evaluationResult`. Without this, an in-flight Claude call from post A would write its result into the state for post B after the user switches, causing the evaluation panel to show stale data for the wrong post. `executeEvaluation` checks `Task.isCancelled` after `await` and catches `CancellationError` to exit cleanly without writing state.
- **`syncContentToSwift` mechanism for AI-generated posts** — when AI generates a full post, `contentSyncPending` is set to `true`. `EditorView.updateNSView` propagates this to `EditorCoordinator.syncAfterNextSetContent`. After `setContent` pushes the HTML to WKWebView, `syncContentToSwift()` is called to force a `contentChanged` message back to Swift, ensuring the autosave timer captures the generated content. The sync fires even when `html == lastPushedHTML` (e.g. generating the same content twice) — the flag is consumed after the guard, not before.
- **Confirmation dialogs are native `.alert`s, and the roles carry the styling** — Revert ("Revert to Server Version?"), Replace ("Replace Content?"), Conflict ("Conflict Detected") and Truncation ("Post may be cut off") were hand-built `.sheet`s with a bordered-prominent primary and `.keyboardShortcut(.return, modifiers: .command)` until the native-ui branch. They now use `.alert` with `role: .cancel` and `role: .destructive`, so macOS supplies the layout, the button order and the Return/Escape bindings — ⌘↩ is no longer bound on any of them, and the user guide (`site/docs.html`) documents plain Return. `.alert` dismisses itself before running a button action, so the binding no longer needs resetting by hand; the one sheet that remains is Generate, which is a real form rather than a confirmation.

- **`PostPayload.encode(to:)` is hand-written, so a new payload field is silently not sent** — the side-door decode that puts `core/footnotes` bodies in `meta` forced a custom encoder; adding a property to `PostPayload` does nothing until it is also written there, and the failure is a field quietly missing from the REST request rather than a compile error. `everyOtherFieldStillEncodesAlongsideMeta` in `Tests/QuillTests/PostPayloadTests.swift` is the guard to extend.
- **`EditorCoordinator.setContent` dedupes on the HTML *and* the footnotes** — footnote bodies live in post meta, so two posts can share a body and differ only in their notes. `EditorPushState` holds both halves; `contentChanged` records the HTML and `footnotesChanged` records the notes, so neither handler can leave the other stale.
- **`LinkPickerView`'s field follows the house text-field style** — it drew its own `RoundedRectangle` that flipped to `Color.accentColor` on focus, which no other field in the app does; the `@FocusState` existed only to drive that ring and went with it (2026-09-19). The search results stay plain `.buttonStyle(.plain)` rows rather than a `List`: this is a click-to-pick dropdown inside an `NSPopover`, where a `List` adds row selection state and inset sizing that fight the behaviour.
- **The block-risk banner's "Save anyway" button is a plain `.bordered` button** — it was hand-drawn with an explicit background, under a comment saying the app's amber accent made `.bordered` invisible. The amber accent is gone, so the workaround went too (2026-09-19).
- **The inspector's `.background(InspectorTitlebarFix())` is load-bearing** — without it the panel's background stops below the toolbar on every reopen after the first, and the whole toolbar fades for 0.25s on every toggle. Full explanation of both in `docs/gotchas.md`.
- **No `.fixedSize(horizontal: false, vertical: true)` on wrapping text in the editor column** — it turns the text's wrapped height into the column's minimum height, so every split-view width change moves the minimum and AppKit aborts with an update-constraints loop (`_postWindowNeedsUpdateConstraints`). The block-risk banner crashed Quill on every post with an unsupported block until it was removed (2026-09-21); plain `Text` in a `VStack` already wraps.
- **Pasted images reach Swift as data URLs through `uploadPastedImages`** — WebKit gives the page a pasted screenshot or Finder image as `clipboardData.files`, and Word's images arrive inside the HTML as `data:` URLs, so no `paste:` override is needed. The editor posts `{ images: [{ token, dataURL }] }`. `PastedImage.decode` refuses anything but a base64 image data URL, and decoding runs off the main thread. A `nil` token means insert at the cursor, like a drop; a token means the image is already in the document, and `window.resolvePastedImage(token, url, mediaId)` swaps its source once uploaded; the swap is dispatched with `addToHistory: false`, so one ⌘Z after an upload takes back the whole paste and a redo brings back the uploaded URL. `handlePastedImages` releases every token when it finishes, through `PastedImage.forgetScript` → `window.forgetPastedImage` in a `defer`: on success, on a failed upload, with no credentials, on a temp-write failure, and for entries `PastedImage.decode` rejects. A token left live makes the editor skip that image, so pasting it again would never retry. The upload joins `dropTask` (see the `uploadStatus` gotcha in `docs/gotchas.md`). The extension comes from the bytes (`fileExtension(for:mimeType:)`), because Word labels its JPEGs `image/png`. Full pipeline: `docs/paste.md`.
- **A dropped or pasted image goes only to the post it was dropped on** — the drop and paste handlers capture `loadedItem?.id` before joining `dropTask`, and each upload's placement closure inserts (through `EditorHandle.insertImage`, not `.insertMediaURL`) or swaps a pasted image's source only while `loadedItem` and `appState.selectedItem` still hold that ID and the editor web view is still in a window. The window check covers a section round-trip: the selection comes back to the same post, but the view that queued the upload was torn down, so its web view is dead. Otherwise the image stays in the Media Library and the toast says it was not inserted. Known limit: after a section switch that toast is drawn on the torn-down view, so the user sees no message; the image is in the Media Library. `.insertMediaURL` is broadcast to every live coordinator and carries no post, so it is left to the media picker sheet, which is modal on the open post.
- **Settings count toward `isDirty`; only the body goes in the autosave stash** — `cleanSettings` is the settings baseline, set wherever `cleanTitle`/`cleanContent` are (`applyRemotePost`, the local-draft load, Save Draft, and a save, where it is the settings that were sent). `isDirty` is `bodyIsDirty || settings != cleanSettings`, so a settings-only change shows the edited dot and Revert. The stash holds title, content and footnotes only, so `flushToDB` and `performAutosave` skip a remote post whose body is clean; writing an unchanged body would restore on the next open with an "Unsaved changes restored" toast. A settings-only change on a remote post is therefore still lost when the user leaves the post. `PostSettings(post:)` is the one mapping from a `WPPost`.
