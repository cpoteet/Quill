# Media views (MediaPickerView, GallerySheet, MediaLibraryView, MediaGalleryView, MediaPreviewOverlay, MediaSidebarSection, MediaDetailView)

Implementation gotchas specific to this directory, split out from the project root `CLAUDE.md` (2026-07-11) to keep the root file lazy-loaded. See the root `CLAUDE.md` for architecture, build/test commands, and cross-cutting conventions.

## Known gotchas

- **A `TextField` inside a `List` row with `.onMove` barely takes focus — the drag gesture claims mouse-down first** — `GallerySheet`'s expandable alt/caption rows hit this: clicks on the fields mostly did nothing, while every automated test stayed green (no SwiftUI harness exists here — this class of bug is only findable by using the app). Fix is `.moveDisabled(expandedIDs.contains(sel.id))` on the row, so a row opts out of reorder exactly while it's being edited. Two things must stay in sync with it: (1) the open-hand hover cursor has to be suppressed on an expanded row *and* over its chevron/X buttons, or the row advertises a drag it will refuse; (2) collapse-to-restore-dragging fires on **hover** of the grip, not on click — `moveDisabled` is read when the row is built, so AppKit has already ruled the drag out at mouse-down, and a click would be spent collapsing rather than dragging.
- **`GallerySheet.toggle(_:)` must clear `expandedIDs` when it deselects, not just when it collapses a row** — `expandedIDs` is keyed by media id and outlives `selected`, so deselecting an expanded image in the grid left its id behind; re-selecting the same image brought the row back already expanded and therefore already `.moveDisabled(true)` (see the `TextField`-vs-drag gotcha above), i.e. silently un-draggable for no visible reason. `toggle` now calls `expandedIDs.remove(media.id)` on the deselect branch. Any future per-row state keyed by media id needs the same treatment — there is no SwiftUI harness here, so this is manual-checklist territory (`docs/testing-plan.md` §7.4).
- **`GallerySheet.selected` is `[GallerySelection]`, not `[WPMedia]`** — each entry carries the media item plus the `alt`/`caption` destined for *this* gallery, seeded from `media.altText`/`media.captionText` and sent as the `alt`/`caption` keys in the insert payload. Edits are block-local and never write back to the media library. `GallerySelection` is `public` because `GallerySheet.init` is public. Alt/caption are insert-time only: an inserted gallery is still a read-only card, so fixing a typo means Code View or re-inserting (see `docs/superpowers/specs/2026-08-13-gallery-image-alt-caption-design.md` for why re-editable galleries were rejected).
- **Gallery `image.url` is the display-size URL, not the full-resolution original — `image.fullUrl` carries the latter** — `GallerySheet`'s Size picker resolves each selected image to a specific size via `WPMedia.sizedURL(for:)` and sends that as `image.url` in the insert-gallery JSON payload; this is correct for `<img src>` but was also being reused for the `linkTo: 'media'` anchor's `href`, so choosing e.g. Size=Thumbnail with Link To=Full Image silently linked to the thumbnail file instead of the original. Fixed by sending a separate `fullUrl: media.sourceURL` field alongside `url`; `galleryBlock`'s `renderHTML` reconstruction path in `editor.html` uses `image.fullUrl || image.url` for the anchor href specifically (falls back to `url` for older/other callers that don't send `fullUrl`). Only affects the reconstruction path (sheet-inserted galleries) — loaded galleries render via `sourceHTML` verbatim and were never affected.
- **Shared upload-from-disk helpers: `pickImageFromDisk()` / `uploadPickedImage(_:credentials:)`** (top-level funcs in `MediaPickerView.swift`) — `MediaPickerView` and `GallerySheet` both offer an inline "Upload" button that opens `NSOpenPanel` and uploads via `WordPressClient.uploadMedia`; this logic is factored into these two shared functions so the two flows can't independently drift. Each view still owns its own state update after upload (`MediaPickerView` inserts into `mediaItems`; `GallerySheet` inserts into `mediaItems` *and* appends to `selected`, so an uploaded image is immediately part of the gallery being built — do not drop the `selected.append` half, that was the point of adding the button to the gallery picker in the first place).
- **`MediaThumbnail`** (in `MediaPickerView.swift`) — shared grid-cell view for both `MediaPickerView` and `GallerySheet`, parameterized by `isSelected: Bool = false` (adds accent-color stroke + checkmark overlay, used by `GallerySheet`) and `size: CGFloat = 90` (`GallerySheet` uses 80). Do not reintroduce a second copy of this view for a future *picker* — extend the parameters instead. `MediaGalleryThumbnail` (in `MediaGalleryView.swift`) is a deliberate exception, not a duplicate: it scales to the collection-view cell rather than a fixed size, carries a filename label, and falls back to document/PDF icons because the library gallery shows PDFs and audio while the picker never does. Folding the two together would add four parameters to a view used in three places.
- **`MediaPickerView` is picker-only** — The `.browser` case and `MediaPickerMode` enum have been removed. `MediaPickerView` is now a sheet-only picker used for inserting images into the editor. The media sidebar (`MediaSidebarSection`) handles browsing. Do not add a `mode:` parameter back.
- **`MediaLibraryView` reloads on `.task(id: reloadKey)`, and `reloadKey` is filter + search + refresh token** — the old `.onAppear` reload on `MediaSidebarSection` is gone. All three components matter. Filter and search change the query. `appState.mediaRefreshToken` exists solely so the toolbar Refresh button can force a reload without changing the query, because `loadMedia` always reads the current filter. Dropping the token silently makes Refresh a no-op in the Media section, which is exactly the bug the native-ui branch shipped (`case .media: break`).
- **Thumbnail views anchor layout with `Color.clear`, never with `AsyncImage` directly** — `AsyncImage` participates in SwiftUI layout and reports its natural image dimensions once loaded, which breaks grid column sizing (wide images span two columns, rows misalign). Use a `Color.clear` frame as the layout anchor and put `AsyncImage` inside `.overlay { }`, which fills the parent's bounds without affecting layout. `MediaGalleryThumbnail` and `MediaThumbnail` both follow this. The deleted `MediaSidebarCell` did too.
- **`MediaThumbnail` in `MediaPickerView` follows the same `Color.clear` pattern** — uses `Color.clear.frame(minWidth: 0, maxWidth: .infinity, minHeight: 90, maxHeight: 90)` with `AsyncImage` in `.overlay { }`. Grid uses 3 fixed `GridItem(.flexible())` columns with `.contentShape(Rectangle())` on each cell. Do NOT use `GridItem(.adaptive(minimum:))` — adaptive columns give cells widths larger than the fixed thumbnail, so tap targets don't cover the full cell area and taps register on the wrong image.
- **`MediaGalleryView` syncs selection in both directions, and `Coordinator.isApplyingSelection` is what stops the loop** — SwiftUI pushes `selection` into the `NSCollectionView` in `apply(items:selection:)`, and the collection view pushes user clicks back out through `didSelectItemsAt`. Without the flag, a SwiftUI-driven selection echoes back as if the user had made it, and the two sides ping-pong. Do not remove it.
- **`onNeedMore` fires on every scroll notification, not once per page** — it is driven by `NSView.boundsDidChangeNotification`, which posts continuously while scrolling. The `hasMore` and `isLoadingMore` guards in `loadMoreMedia` are the only thing between that and one HTTP request per scroll event.
- **`NSOpenPanel.runModal()` bails silently if called during a SwiftUI view update** — it returns `.cancel` in about 0.3 seconds and no panel ever appears. This is why `startUpload()` wraps the call in `DispatchQueue.main.async`. It matters because the upload is triggered from `.onChange(of: appState.triggerMediaUpload)`, which runs inside the view-graph update. Calling `uploadFromDisk()` straight from a `Button` action works, which is why the old bottom-strip button worked while the File → New Media path did not.
- **`appState.mediaItems` now holds the *filtered* list, and the editor reads it as a size cache** — `PostEditorView` looks there first for an image's `mediaDetails.sizes` to draw the Thumb/Medium/Large/Full buttons. Under a filter the array can miss an image the editor wants, and the editor falls back to `WordPressClient.fetchMediaItem`. The buttons still appear; the cost is one request. That fallback is load-bearing — do not "optimise" it away.
- **Background computer-use clicks do not select items in `MediaGalleryView`** — the same limitation the editor's `CLAUDE.md` records for the `WKWebView`. `NSCollectionView` selection needs real mouse input, and the accessibility tree exposes the items as plain `AXGroup`s with no press action. Verifying selection, arrow keys or the preview overlay requires full-screen control, not the `app_*` background tools.
- **`.inspector(isPresented:)` takes a plain binding to one flag; do not give it a derived `get`** — an earlier version used `get: { isMediaInspectorOpen && selectedMedia != nil }` so the panel could never show with nothing selected. Deriving the value means SwiftUI's own write-backs fight the expression. The panel now binds straight to `$appState.isMediaInspectorOpen` and its content handles the empty case with a "No Selection" placeholder. Historical note on the derived form, kept because the trap is easy to re-introduce: such a binding must ignore writes of `true` — SwiftUI writes back to the binding during layout, not only when the user closes the panel. `set: { appState.isMediaInspectorOpen = $0 }` therefore re-opened the inspector immediately after the toolbar button closed it, making the button look dead. Write only the `false` direction, as `PostEditorView.swift:287` already does. This was latent while the flag was a local `@State` and only appeared once it moved to `@Published` on `AppState`, because the write-back then triggered a re-render. Moving state from `@State` to `@Published` is not a neutral refactor when a two-way binding reads it.
- **An AppKit callback can set an ordinary `@Published` value, but it cannot drive `.inspector(isPresented:)` directly** — traced with logging, not guessed. "Show Details" sets the flag and a read-back confirms it is `true`, yet SwiftUI never re-presents the inspector and its binding's `set` is never called. `selectedMedia` set from the very same callback propagates fine, so this is specific to the presentation binding, not to AppKit-to-SwiftUI state in general. The fix is the pattern `triggerMediaUpload` already uses: the callback sets `appState.triggerShowMediaDetails`, and a SwiftUI `.onChange` in `MediaLibraryView` flips `isMediaInspectorOpen` from inside a view update. `DispatchQueue.main.async` does NOT fix this one — that was tried first and failed.
- **Three media grids exist, and that is a decision, not drift** — `MediaGalleryView` is a real `NSCollectionView` for the main Media panel; `MediaPickerView` and `GallerySheet` each keep a plain `LazyVGrid`. Reviewed on 2026-09-19 and kept: the collection view carries keyboard navigation, multi-select and a context menu that neither picker sheet needs, so reusing it means adding a single-select mode and a multi-select mode to a control that currently has one job. Reopen this only if a picker starts needing keyboard navigation.
- **All three media grids page on scroll; none has a Load More button** — `MediaPickerView` and `GallerySheet` used one until 2026-09-19. Their trigger is `.onAppear` on the **last cell**, not a sentinel view under the grid: a sentinel that is already on screen never re-appears, so the second page never loads. Appending items creates a new last cell, which is what re-arms the trigger. Two things this depends on: (1) `loadMoreMedia` now guards on `hasMore, !isLoadingMore` itself — the `if hasMore` wrapper and `.disabled(isLoadingMore)` on the old button were the only guards, and `.onAppear` can fire more than once per cell, so without the guard a scroll means duplicate requests and duplicate rows; (2) `loadMoreMedia` loops until a page yields at least one image, because both grids filter to `mediaType == "image"` while the library also holds PDFs and audio — a full page of non-images would leave the last cell unchanged with nothing left to re-arm the trigger, stranding the grid with `hasMore == true` and no way to continue.
- **Both sheets use the macOS bottom action bar** — `MediaPickerView` and `GallerySheet` put the title top-leading, `Upload…` bottom-leading, and Cancel (plus Insert Gallery) bottom-trailing. They used an iOS-style top header bar until 2026-09-19. See `docs/gotchas.md` for the rule.
