# API layer (WordPressClient, Models)

Implementation gotchas specific to this directory. See the root `CLAUDE.md` for architecture, build/test commands, and cross-cutting conventions.

## Known gotchas

- **`WPMedia.sizedURL(for:)`** — resolves a WordPress size slug to its URL: `"full"` always returns `sourceURL`; any other slug looks up `mediaDetails.sizes[slug].sourceURL`, falling back to `sourceURL` if that entry is missing OR its `source_url` decoded to an empty string (mirrors the existing `thumbnailURL` computed property's `!url.isEmpty` guard — `MediaSize.sourceURL` decodes a missing/blank JSON key to `""`, not nil, so a bare `??` on the optional chain would not catch a populated-but-blank size entry). Use this instead of re-deriving size-slug URL resolution inline at a call site. **This fallback is not automatic for other code reading `media_details.sizes` directly** — `EditorCoordinator.mediaSizesDict(for:)` (feeds the JS image toolbar's size buttons and the "Link to Full Image" toggle via `requestMediaSizes`/`setMediaSizes`) originally built its dict straight from `mediaDetails.sizes` with no fallback, so any media item whose sizes dict omitted a `"full"` entry (common — WordPress often only lists generated intermediate sizes) silently disabled both the Full-size preset button and the link toggle even with a valid `mediaId`. Fixed by synthesizing a `"full"` entry from `media.sourceURL` when missing, same as `sizedURL(for:)` does. Any new consumer of `media_details.sizes` needs this same fallback — it doesn't come for free.
- **Pages endpoint** omits `categories` and `tags` fields — `WPPost` uses `decodeIfPresent` with `[]` defaults; do not make those fields required again
- **`WPPost.type` field** — set to `"post"` or `"page"` by the API; used throughout `PostEditorView` and `WordPressClient` to route to the correct endpoint (`/posts/` vs `/pages/`). Do not remove this field.
- **`WPPost.dateGmt` field** — decoded from `date_gmt` JSON key (UTC). Used in `PostEditorView.loadItem()` for scheduling round-trips. `PostPayload` sends scheduled dates as `dateGmt` (JSON key `date_gmt`) — never use `date` for scheduling; WordPress interprets `date` as site-local time and ignores timezone suffix.
- **Credential store** — `WordPressClient` must use ephemeral URLSession; switching to `.shared` will re-introduce keychain prompts during network calls
- **`AutosaveResponse` type** — the WordPress autosave endpoint (`/posts/{id}/autosaves`, `/pages/{id}/autosaves`) returns a partial object, not a full `WPPost`. Only `link?` is decoded into `AutosaveResponse`. The preview URL is built as `autosave.link ?? post.link` to handle sites that omit `link` from the autosave response.
- **MIME type lookups use `MimeType.forFile(url)`** (`Sources/QuillKit/API/MimeType.swift`) — backed by `UTType.preferredMIMEType`, not a hand-maintained switch. `PostEditorView`, `MediaSidebarSection`, and `MediaPickerView` all call this one shared helper. Do not add another local `mimeType(for:)`/`imageMimeType(for:)` function — that's exactly the drift this replaced (the three copies had already disagreed on which extensions were supported).
- **`NetworkFailure.isConnectivity(_:)`** (`Sources/QuillKit/API/NetworkFailure.swift`) — decides whether a transport error means "couldn't reach the server" by its `URLError` code, never by `localizedDescription` text (that text is localized, so an English substring match failed on every non-English system). Used by both `APIError.networkError` and `AnthropicError.networkError`; each keeps its own message text, only the condition is shared. Add codes here, not to a local check in either error type. `APIError` checks `.notConnectedToInternet` first and says the Mac is offline, since the site message tells the user to check the URL. Tests: `NetworkFailureTests`.
- **`APIError.isFixedInSettings` must match the message the error shows** — the sidebar error row offers Open Blog Settings… only when it returns true, so it covers exactly the errors whose text sends the user to Settings: 400, 401, 403, `.invalidURL`, `.unexpectedHTML`, `.notConnected`, and a connectivity `networkError` (host not found, timed out) other than `.notConnectedToInternet`, whose message says the Mac is offline. Change a message and this switch together. Tests: `ErrorMessageTests.settingsFixableErrors` / `errorsSettingsCannotFix`.
- **`URLComponents`/`URLQueryItem` leaves a literal `+` unescaped** in query values (valid per RFC 3986), but WordPress/PHP decodes `+` as a space. `WordPressClient.endpoint(_:query:)` post-processes `percentEncodedQuery` to escape `+` → `%2B` after building it via `queryItems`. Keep this post-processing step if the query-building code is ever refactored.
- **Trash vs. force-delete** — `WordPressClient.trashPost/trashPage` call `DELETE /posts/{id}?force=false`, which moves to WordPress Trash (recoverable). `force=true` would permanently delete. Do not change the `force` parameter unless permanent deletion is explicitly intended.
- **`performVoid` helper** — `WordPressClient` has a private `performVoid(_:)` alongside `perform<T>(_:)`. Use `performVoid` for DELETE (and any future) calls that don't need to decode a response body. Do not use `perform<T>` with a dummy decodable type just to discard the result.
- **`WPPost.parent` and `WPPost.commentStatus`** — both use `decodeIfPresent` with defaults (`0` and `"open"`). `PostPayload` sends `parent` only for pages (nil for posts); `commentStatus` is always sent. `slug` is sent only when non-empty (nil omits it from the request, leaving the server value unchanged on update).
- **`MediaDetails.width`/`height` as floats** — The WordPress REST API returns `media_details.width` and `height` as JSON floating-point numbers (e.g. `2560.0`) for some media items. Swift's `Int` decoder rejects these. `MediaDetails` and `MediaSize` use a try-Int-then-Double pattern in their `init(from:)` to accept both. Do not change these back to a bare `decodeIfPresent(Int.self, ...)` call.
- **`deleteMedia` is permanent** — `WordPressClient.deleteMedia(id:)` calls `DELETE /media/{id}?force=true`. WordPress media items have no trash state — deletion is immediate and irreversible. Always show a confirmation alert before calling it.
- **`uploadMedia` takes `fileURL: URL`, not `data: Data`** — uses `URLSession.upload(for:fromFile:)` to stream without buffering the file in RAM. Do NOT call `Data(contentsOf:)` and pass the result; always pass the file URL directly. Drop-path reads must also happen off the main actor to avoid freezing the UI on large files.
- **`WPMedia.thumbnailURL`** — computed property that prefers `media_details.sizes["thumbnail"].source_url`, falling back to `sourceURL`. Use this in `AsyncImage` for grid cells instead of `sourceURL` — avoids downloading full-resolution originals (often 2–8 MB) at 80–90 pt thumbnail sizes.
- **`RenderedString.editorHTML` computed property** — use this instead of `raw ?? rendered` anywhere you load post/page **content** into the editor. `raw` can be an empty string `""` or whitespace-only `"\n  "` (WordPress sends this for posts with no `context=edit` access), which would clear the editor even though `rendered` has valid HTML. `editorHTML` returns `raw` only when it is non-empty after trimming; otherwise falls back to `rendered`. Classic (pre-Gutenberg) content — detected by absence of `<!-- wp:` comments, `<p>` tags, **and** a `wp-block-` class substring — is run through `wpautop()` which wraps text in `<p>` tags, converts single newlines to `<br />`, and separates block-level elements. The `wp-block-` check exists because `gutenbergPassthrough` (`Sources/QuillKit/Resources/editor-transforms.js`) explicitly supports round-tripping class-only Gutenberg block markup with no `<!-- wp: -->` comment and no `<p>` tag at all (e.g. a post consisting entirely of an Accordion/Columns block) — without it, such a post gets misclassified as classic and corrupted by `wpautop()` before the JS-side parser ever sees it, on the very next load after a save. Do NOT revert call sites to `raw ?? rendered` or `raw ?? ""`, and do NOT remove the `wp-block-` check from this heuristic.
- **`RenderedString.excerptText` computed property** — use this for **excerpts only**, never `editorHTML`. `excerptText` reads only `raw` (strips HTML, decodes entities); if `raw` is empty or nil it returns `""`. It never falls back to `rendered`, because `rendered` contains WordPress's auto-generated excerpt (wrapped in `<p>` tags from the post content). Using `editorHTML` for excerpts caused a false-adoption loop: the auto-generated HTML rendered excerpt would populate the excerpt field, then get saved back as a manual excerpt on the next save. Do NOT use `editorHTML` for excerpt loading.
- **`RenderedString.decodedTitle`** — returns `rendered.decodingHTMLEntities()`. WordPress returns `title.rendered` with HTML entities (e.g. `&#8217;` for smart apostrophes). Use `decodedTitle` anywhere post or media titles are displayed in the UI. The `decodingHTMLEntities()` String extension handles numeric (`&#8217;`), hex (`&#x26;`), and named entities (`&amp;`, `&ldquo;`, etc.).
- **`WPMedia.caption` / `captionText`** — `caption` decodes from the `caption` key as `RenderedString?`; `captionText` reuses `RenderedString.excerptText`, so it reads `raw` **only** and returns `""` for a rendered-only payload. Fine for `fetchMedia`/`fetchMediaItem` (both use `context=edit`, so `raw` is present), but an `uploadMedia` response has no `context=edit` and therefore yields `""` rather than the rendered HTML — correct here, since a just-uploaded image has no caption anyway. Prefills the gallery sheet's per-image caption field.
- **`WPMedia.altText`** — decoded from `alt_text` JSON key (default `""`). Populated on insert via the media picker and drag-drop. Editable in `MediaDetailView` via `onSaveAltText` callback (wired in `ContentView` to `WordPressClient.updateMediaAltText`). Pre-populates the `<img alt="...">` attribute in the editor when inserting from the media library. The image toolbar's Alt row reads/writes `node.attrs.alt` via `setNodeMarkup`.
- **`SiteDiscovery.discover` asks for JSON, decodes the site name, and adopts a redirect only on the same site** — it sends `Accept: application/json` for the same reason `WordPressClient` does (QA #151: WordPress hides PHP warnings for a JSON request, which would otherwise come ahead of the index and fail the decode). The REST index's `name` holds HTML entities (`&#039;`, `&amp;`), so it goes through `decodingHTMLEntities()` before the onboarding panels show it. The address the index was answered at is adopted only when `sameSite` passes: HTTPS (or http on a loopback host), the same scheme and port as the typed address, and the typed host or its `www`/bare twin. Any other redirect (a downgrade to http, another host or port) keeps the typed address, so a proxy or a hostile redirect cannot point Quill's authenticated calls elsewhere. Tests: `SiteDiscoveryTests`.
